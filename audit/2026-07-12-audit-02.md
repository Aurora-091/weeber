**Discount percentage scale — cross-repo dependency, now correct (but fragile):**
- openvent's `offerCartRecoveryDiscount` tool sends `value: percentOff` as a **whole number** (1–30).

  created was 10×–30× over 100% (a 1000%+ discount). The scale contract is now correct end to end, but it
  is **implicit** — nothing in openvent's repo documents that it must send whole numbers, because…

## PART B — Defects & findings (priority ordered)

### 🔴 F1 (P0 / critical) — Scheduled calls are Twilio-only; the entire Shopify automation is silently broken for Plivo/Exotel BYO orgs

This is the headline. The manual/inbound outbound path (`voice/routes.ts`) correctly branches on
`org.telephonyProvider` (twilio / plivo / exotel) — a merchant's dashboard **test call** works on any
provider. But the **scheduler** (`workflows/scheduler.ts`'s `executeDueScheduledCalls`), which is what
actually drives *every* Shopify automation — cart recovery, COD confirmation, feedback, all of which flow
through the `scheduledCalls` table — dials **unconditionally through Twilio**:

```
const call = await (await getTwilioClientForOrg(row.orgId)).calls.create({ to, from, ... })
```

and `getTwilioClientForOrg` (twilio-client.ts) **falls back to the platform Twilio client** when the org
has no Twilio creds (`lookupOrgCreds` reads only `twilioAccountSid`/`twilioAuthToken`). So for a
Plivo/Exotel BYO org:
- `from` = `org.outboundNumber` (a **Plivo/Exotel** number),
- placed via the **platform Twilio** account,
- → Twilio rejects it (the `from` isn't a Twilio-owned number on that account), and the call is marked
  `failed` in the sweep's catch block. Silently. No merchant-visible signal.

**Concrete consequence:** an India-first merchant onboarded on Plivo or Exotel (the entire reason that BYO
work exists) gets a working test call and working inbound, but **zero automated cart-recovery / COD /
feedback calls, ever.** The whole India telephony investment doesn't reach the automation spine — it stops
at the manual path.

**This is not visible from inside either repo alone** and no test covers "scheduled call for a non-Twilio
org," which is why it survived. **Recommend (before any India pilot):** route the scheduler's outbound
through the same provider-branch the manual route already has — factor `routes.ts`'s
twilio/plivo/exotel dispatch into one shared `placeOutboundCall(org, ...)` and call it from *both* the
manual route and the scheduler. Add a test: "scheduled call for a plivo org calls the plivo client, not
Twilio."

### 🟠 F2 (P1) — Exotel outbound audio chunks not guaranteed to be a 320-byte multiple
Already flagged in-code (telephony-transport.ts) and in `india-telephony.md` on the 2026-07-12 re-check —
crediting that. Confirming it's **real and will bite on the first live Exotel call**: Exotel's audio-format
spec requires each outbound media chunk be 3,200–100,000 bytes **and a multiple of 320**. The Exotel
adapter transcodes whatever chunk size the TTS provider naturally emits (mu-law → PCM16), with no
re-chunking to that boundary. Off-boundary chunks typically manifest as clicks/garbled playback or dropped
frames, not a clean error — hard to diagnose live. **Recommend:** add a small output ring-buffer in the
Exotel adapter that only flushes 320-byte-aligned frames (buffer the remainder). Do it before the Exotel
pilot, not after the first "why does the bot sound broken" report. Low effort, isolated to one adapter.

### 🟡 F4 (P2) — Carry-over from audit #01: `recovered_amount` still `text`
`schema.ts:230` — `recoveredAmount: text("recovered_amount")`, and `orders/create` stores
`String(total_price)` into it. Audit #01's D4 recommended moving to a numeric type *before* real orders
exist (cheap now, migration cost later). Still open. Any future revenue-attribution dashboard summing
recovered value inherits cast-on-every-query + silent format-drift risk (`"599.00"` vs `"599"`). Same
recommendation stands; the window to fix it cheaply is still open but closes at first production order.

## PART C — Confirmed working well (verified in code + against live docs)

- **Telephony provider abstraction** (`telephony-transport.ts`) is clean: one mu-law-8k internal shape,
  per-provider wire adapters, Exotel PCM16↔mu-law transcode isolated to its adapter. Wire formats
  **verified against live docs (2026-07-12):** Exotel Voicebot = bidirectional WS, 8kHz 16-bit PCM
  (Pipecat + ElevenLabs docs confirm); Plivo = mu-law, `playAudio`/`clearAudio` frames; Twilio = the known
  `streamSid`/`clear` format. All match the code.
- **Plivo `RequestUUID` vs `CallUUID` fix** (commit b0aed45) is correct — re-verified against Plivo's Calls
  API docs. The prior version keyed session lookup off the wrong id and would have silently lost outbound
  persona/org context; the fix binds via the documented `answer_url` correlator. Good catch, good process
  (found via live-doc re-verification, not training recall).
- **Graph workflow engine** (`graph-engine.ts`) is a proper state machine: trigger→wait→call→
  conditionalSplit, with the call node parking the run and `advanceWorkflow(runId, outcome)` resuming on
  call outcome. Discount escalation per attempt (`resolveDiscountPercent`, clamped) is sensible.
- **Scheduler compliance gates** — DNC + calling-window checked on *scheduled* retries too, atomic
  `pending→claimed` row claim prevents double-dial. (The provider bug F1 is orthogonal to this — the
  guardrails themselves are right.)
- **Idempotency + honest status codes** across the Shopify contract — mark-after-side-effect ordering is
  correct (crash mid-effect → retry re-processes, doesn't skip).
- **Voice stream loop** (`stream.ts`) is defensively written and provider-agnostic; independent
  prompt-injection phrase detector as defense-in-depth alongside model self-reporting.

## Resolution — fixes applied (2026-07-12)

All four findings fixed. Verified green: `turbo typecheck` (3/3), `oxlint` (0 warnings / 0 errors),
`turbo test` (@openvent/compliance 34, @weeber/api 176, @weeber/web 8 — all pass).

### F1 (P0) — FIXED. Scheduler now dispatches per provider.
- New shared module `packages/api/src/voice/place-outbound-call.ts` — `resolveOutboundRouting()` +
  `placeOutboundCall()`. Single call-placement entry point that dispatches to the org's real provider
  (Twilio / Plivo / Exotel) and returns a provider-agnostic `{ sessionKey, status }`.
- `workflows/scheduler.ts` now calls `placeOutboundCall()` instead of hard-coding the Twilio client, so a
  Plivo/Exotel (India BYO) org's scheduled retries dial on the correct account instead of silently falling
  through to platform Twilio.
- `voice/routes.ts` `/calls/outbound` refactored onto the *same* `placeOutboundCall()`, so the manual and
  scheduled paths can no longer drift. Compliance gates, per-call session fields, and response shapes
  unchanged.
- Coverage added: `scheduler.test.ts` now proves a Plivo org and an Exotel org each route to their own
  client (`createPlivoOutboundCall` / `createExotelOutboundCall`) and **not** Twilio.

### F2 (P1) — FIXED. Exotel outbound is frame-aligned.
- `telephony-transport.ts` Exotel `buildOutboundMedia` now pads each outbound PCM16 packet up to the next
  320-byte (20ms @ 8kHz/16-bit) boundary with silence via `padToFrameMultiple()`, so Exotel's VoiceBot
  applet never receives a partial frame. Trade-off (sub-20ms silence per chunk vs a stateful re-framer that
  would need per-stream state the shared transport singleton can't safely hold) documented in code; revisit
  once a live Exotel call validates the path.

### F3 (P2) — FIXED. Contract restored + version aligned.
- `docs/contract.md` added to openvent as a byte-identical copy of weebersh's (both now at **v1.5**).
- weebersh's contract header was also bumped 1.4 → 1.5 (its changelog already documented 1.5; only the
  header line was stale) so the two copies match exactly.
- `integrations/shopify/routes.ts` header comment corrected from "contract v1.4" to "v1.5". The two
  remaining "changed in 1.4" comments are accurate history (they attribute when that specific behavior was
  introduced, matching the contract changelog) and were left as-is.

### F4 (P2) — FIXED. `recovered_amount` is money, not text.
- `database/schema.ts`: `recovered_amount` changed from `text` to `numeric(12, 2)` — exact decimal, no float
  drift, SQL-aggregatable. Drizzle returns `numeric` as a string, so the existing defensive
  `Number.parseFloat` read path in `org-queries.ts` is unchanged.
- Migration `drizzle/0014_jittery_menace.sql` generated (`text` → `numeric`). It also captured a pre-existing
  drift — `platform_settings` was in the schema but never in a migration (applied via `db:push`); its
  `CREATE TABLE` was made `IF NOT EXISTS` so the migration is safe on already-pushed databases. Run the
  migration before deploy.
