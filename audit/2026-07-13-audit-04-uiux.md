## Findings — Priority Ordered

### 🟠 P1 — Workflow save button shows "Saved" permanently after the first save, even with new unsaved edits (both merchant and admin editors)

**`packages/web/src/web/pages/app/workflows.tsx`** line 114 and
**`packages/web/src/web/pages/dashboard/workflow-editor.tsx`** line 228, identical pattern:

```tsx
{save.isSuccess ? "Saved" : "Save changes"}
```

`save` is a React Query `useMutation`. `isSuccess` stays `true` forever after the first successful
`mutate()` call — it is never reset. Editing a node's config after that first save (`setNodeOverride`)
does not touch the mutation's state at all. Result: a user opens a workflow, edits the wait-delay on one
node, clicks Save (button now permanently reads "Saved"), then edits a second node's discount override —
the button **still reads "Saved"**, with no indication the new edit is unsaved. If they navigate away at
that point (no `beforeunload` guard either — see next finding), the second edit is silently lost.

This is not a hypothetical: it's the single most likely way to lose work in the entire canvas feature,
because the whole point of the editor is making several small tweaks across different nodes in one
session.

**Fix**: track a `dirty` boolean that's set `true` on every `setNodeOverride` call and reset to `false`
only in `save`'s `onSuccess`; button label/disabled state should key off `dirty`, not `save.isSuccess`.

### 🟠 P1 — A failed workflow-configs fetch is silently rendered as "no workflows" / "workflow not found," never as an error

**`UserWorkflowsListPage`** (`pages/app/workflows.tsx` line ~254): checks only `workflows.isLoading` and
`rows.length === 0` — never `workflows.isError`. A 401 (expired session), 500, or network failure all
collapse into the exact same empty state as a merchant who genuinely has zero workflows configured:
*"No workflows available — Workflow templates will appear here once your store is connected."* That's a
materially misleading message for what's actually a broken request — it tells a merchant experiencing an
API outage that they haven't set anything up yet, not that something's wrong.

**`UserWorkflowDetailPage`** (same file, line ~312): same gap, worse consequence —
`if (!workflow) return <EmptyState title="Workflow not found" description="This workflow doesn't exist."
/>`. A transient fetch failure on a workflow that absolutely does exist gets reported to the merchant as
"this doesn't exist," which reads as data loss, not a network blip.

The codebase already has the right pattern next door — `call-detail.tsx` line 89:
`{call.isError && <EmptyState title="Conversation not found" description="This call doesn't exist or
isn't yours." />}` — checks `isError` explicitly, separate from the not-found case. The Workflow Canvas
pages just didn't follow the pattern that already existed elsewhere in the same codebase.

**Fix**: add an explicit `workflows.isError` branch to both pages with its own message ("Couldn't load
your workflows — try refreshing") before falling through to the not-found/empty states.

### 🟡 P2 — Theme portal-scoping bug: reconfirmed live, and worse than previously documented (includes dead CSS)

Audit context doc (`docs/UI-UX-AUDIT-CONTEXT.md` §1) already root-caused this; this round reconfirmed it's
still unfixed on current HEAD and found an additional wrinkle nobody had caught:

- `Dialog`, `Sheet`, `DropdownMenu`, and `Tooltip` (`components/ui/dialog.tsx`, `sheet.tsx`,
  `dropdown-menu.tsx`, `tooltip.tsx`) all use their Radix `Portal` with no `container` prop — confirmed by
  reading all four files directly, zero `container=` props exist anywhere in `packages/web`. Default
  Portal target is `document.body`, outside the shell `<div className="theme-weeber ...">` in
  `app-shell.tsx` line ~267. Same bug as documented, still present.
- **New finding this round**: `styles.css` lines 560–567 contain three rules —
  `.theme-weeber [data-radix-dialog-content][data-side="left"]`,
  `.theme-weeber [data-radix-dialog-content][data-state="open"]`,
  `.theme-weeber [data-radix-dialog-content][data-state="closed"]` — intended to animate the mobile
  sidebar's slide-in/out Sheet. **These selectors can never match anything, for two independent reasons
  stacked on top of each other**: (1) the descendant combinator requires the target to be a DOM descendant
  of `.theme-weeber`, which a portaled node never is (the same root cause as the rest of this bug); (2) even
  setting the portal issue aside, `data-radix-dialog-content` isn't an attribute Radix or this codebase's
  `SheetContent` actually emits — `sheet.tsx` line 60 sets `data-slot="sheet-content"`, not
  `data-radix-dialog-content`. So this specific CSS is dead on arrival twice over, not just once. The
  mobile nav Sheet's open/close almost certainly falls back to Tailwind's default `data-[state=...]:animate-*`
  utility classes already present on the same element (line 63 in `sheet.tsx`), so it's not visibly broken
  — but the custom `cubic-bezier` easing and 0.28s/0.22s timing this dead CSS was clearly meant to add is
  silently doing nothing, and would keep silently doing nothing even after the portal-scoping root cause is
  fixed, since the attribute name is wrong too.
- Sonner's `<Toaster />` (rendered at `app-shell.tsx` line ~268) is **not** affected by this bug — it's
  worth noting explicitly, since it'd be an easy false-positive for a future audit to lump in. Sonner
  renders its toast container as a normal in-tree child, not via a manual portal to `document.body`, so it
  correctly inherits `.theme-weeber`/`.dark` — confirmed by `styles.css`'s
  `.theme-weeber [data-sonner-toaster] [data-sonner-toast]` rules (lines 429–448) actually having something
  to match, unlike the dialog-content rules above.

**Status**: not fixed this round (real product-code change, out of this pass's scope per your instruction
— analysis only). Still the single highest-leverage fix on this list: one root-cause change (portal
`container` prop, or promoting `.theme-weeber`/`.dark` to `<body>`) fixes every dialog/sheet/dropdown/
tooltip in the product at once, plus unblocks actually fixing the dead animation CSS above (which should
also have its attribute selector corrected to `[data-slot="sheet-content"]` while someone's in there).

## Workflow Canvas — first-time review (net-new scope this round)

The canvas itself (`components/canvas/{WorkflowNode,BranchEdge,NodeConfigPanel,NodePalette,types,
node-styles,seed-graph}.tsx`, built on `@xyflow/react`) is a legitimate, non-trivial feature that shipped
with no dedicated review until now. Beyond the two P1 bugs above, worth recording what's structurally
sound and what's a known, accepted scope gap rather than a bug:

- **Sensible split**: merchant view (`app/workflows.tsx`) is deliberately read-only on the graph
  (`nodesDraggable={false}`, `nodesConnectable={false}`) with only a side-panel override form for
  `wait`/`call`/`sms` node configs — merchants tune timing/copy, they don't rebuild the flow. Admin view
  (`dashboard/workflow-editor.tsx`) is the real drag-drop editor with `NodePalette`, node add/delete,
  `addEdge`. This is the correct trust boundary, not an oversight.
- **Not a bug, a scope note**: the canvas has no mobile-responsive treatment (fixed-height flex layout,
  drag-based node editing) — reasonable for a desktop-oriented admin/power-merchant tool, but worth
  confirming that's an accepted tradeoff rather than an oversight before anyone reports it as a "broken on
  phone" bug later.
- **Not reviewed this round**: `NodeConfigPanel.tsx`'s validation depth (whether it actually prevents
  saving nonsensical configs, e.g. negative delays) and the admin editor's `Download`/export feature
  (imported but not traced) — flagging as unreviewed, not as clean, for whoever picks up audit #05.
