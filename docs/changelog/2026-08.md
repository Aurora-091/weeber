## 2026-08-12 — A voice belongs to an agent, not a deployment (ADR-102)

ADR-070 settled that a voice is sticky per call and that a voice ID never crosses providers. What it
never audited is what an adapter falls back to when a foreign ID is correctly withheld — and underneath
it, all three TTS adapters read an env var:

```ts
const voiceId = voiceIdOverride || process.env.CARTESIA_VOICE_ID;
```

That reintroduces the hazard ADR-070 exists to prevent, one layer lower. A voice is an **agent**
property — picked per agent in the dashboard, stored in `org_agent_configs.voice_provider` + `voice_id`.
An env var is a **deployment** property. Reading one underneath the other means the same agent row can
speak in a different person's voice depending on which environment served the call.

**And the ElevenLabs failover leg was dead.** Against live Railway production: of 43 env vars,
`ELEVENLABS_VOICE_ID` and `SARVAM_VOICE_ID` are **absent**. All 6 prod `org_agent_configs` rows are
Cartesia with `tts_fallback_order` null, so `DEFAULT_TTS_FALLBACK_ORDER = ["cartesia", "elevenlabs",
"sarvam"]` governs **every call ever placed** — and its second leg resolved its voice ID to `undefined`
and built `wss://api.elevenlabs.io/v1/text-to-speech/undefined/stream-input`. The declared
cross-provider TTS failover has never worked. Nothing said so at boot, nothing said so on the call
record, and it would first have been discovered during a Cartesia incident. ADR-090's class again:
configured, documented, believed, unreachable.

**Shipped:**

- **`FALLBACK_VOICE_BY_PROVIDER`** in `tts/default-voices.ts`, typed `Record<TtsProvider, string>`. A
  missing env var is `undefined` mid-call in production; a missing constant does not typecheck. All
  three entries verified against the live provider APIs, all public and no-extra-cost (a cloned or
  tier-gated voice is another dead leg waiting), all feminine English-first conversational so a
  mid-call failover is heard as a slightly different person, not a change of sex or accent.
- **Cartesia pinned to the exact prod env value** ("Katie - Friendly Fixer"), so no existing agent's
  voice changes. Behaviour-preserving for every call that works today, a repair for the one that never
  did.
- **`resolveVoiceId(provider, voiceId?)`** is now the only way an adapter gets a voice, and it is
  blank-safe — an empty ID used to be interpolated as an empty path segment or empty `voice.id`, which
  each provider rejects differently and none rejects usefully. `DEFAULT_SPEAKER` in `sarvam.ts` deleted
  rather than kept as a second source of truth.
- **Voice IDs leave `assertVoiceConfig`** and both doc surfaces (`docs/reference/getting-started.md`,
  the in-app docs page), so nobody re-adds the variable from documentation.
- **A dead-failover-leg warning at boot.** `assertVoiceConfig` compares both default fallback chains
  against the API keys actually present and warns per unreachable leg. A `warn`, not a `problem` — the
  primary path works and calls connect. Had it existed, this bug would have announced itself on every
  deploy.
- **Tests at the wire, not at the function.** A unit test of `resolveVoiceId` would have passed against
  the broken adapters, so the 10 new tests drive each adapter through a `MockWebSocket` and assert
  `"undefined"` appears in no URL and no payload. Proven to fail for the right reason: restoring the env
  read turns the run red on *"ElevenLabs puts a real voice ID in the URL path, never `undefined`"*.

**Rejected:** setting `ELEVENLABS_VOICE_ID` in Railway (2 minutes, keeps the inversion, recurs for the
next provider); a DB table of default voices (puts a network read on the path that only runs because
something else already broke); failing the call when no voice resolves (the fallback exists *because*
the primary failed); keeping env as a third tier (preserves the exact ambiguity being removed).

**Still open, and a business call rather than a code one:** the ElevenLabs account returns
`{"error":"payment_issue"}` on every generation, so the leg is now structurally correct and still
non-functional, and TTS is effectively single-sourced on Cartesia. Either pay the invoice and treat the
starter tier (40k chars/month) as break-glass only, or accept single-sourcing and record it as a risk.

## 2026-08-12 — A reply too short to trip the buffer was never spoken (ADR-101)

ADR-100 deferred one item as needing its own investigation: 10 of 78 `turn_latency` rows reserved a
turn index and recorded no TTS first byte, called dead air there. **That label was wrong, and it was
hiding the one row that mattered.** Reconciling every turn row against the same call's `transcripts`
by turn order:

- **9 rows, all three columns NULL** — the caller kept talking and aborted the in-flight turn before
  the first LLM token. Correct behaviour, not a defect. Provable rather than inferred: call 25 has 27
  turn rows and 23 agent transcript lines, and the 4 all-NULL rows are exactly the 4 turns with no
  agent line at all, each sitting between two caller lines less than 1.5s apart.
- **8 more rows** at 405–439ms with no `llm_ttft_ms` were also miscounted as "no LLM ran". Those are
  `speakCannedLine` — "Are you still there?" and the goodbye. No LLM is supposed to run on them.
- **1 row is real.** Call 21, turn 3 (2026-08-09): `llm_ttft_ms = 2779`, `tts_first_byte_ms` NULL,
  transcript recording `"OK."` as spoken by the agent, transfer fired immediately after. The caller
  heard silence and was handed off.

**Cause.** ADR-082's tone-tag filter holds streamed deltas back until it can rule out a leading
`[[tone:value]]` marker (the tag arrives split across deltas; half a tag must never be spoken). It
released on the first of three conditions — a complete tag, any `]]`, or 24 characters — and there was
**no condition for end of stream**. A reply shorter than the cap with no `]]` in it satisfied none of
them, so when `generate()` returned the buffer still held every character. ADR-083's lazy connect meant
no TTS socket had ever opened, so `endTurn()` took its "turn produced no speakable text" branch and
resolved cleanly. Nothing errored. Nothing logged. The transcript recorded the line as said.

Every short reply the model does not tag was exposed — "Sure, one moment.", "Got it, thanks.", "OK."
It is 1 turn in 78 rather than 1 in 5 only because the model usually *does* emit the tag it was asked
for. This is the third defect in this one feature (ADR-082: `setTone` silently unwired for months;
ADR-083: socket lifetime burning the failover chain) and ADR-090's class at its purest — the filter was
a closure inside a 2000-line `stream.ts` that no test could reach, while `tone-tags.test.ts` covered
only the pure `stripToneTag` underneath it.

**Shipped:**

- **`flush()`, the missing release condition.** The state machine moves to `tone-tags.ts` as
  `createToneTagFilter({ onTone, onText })` with `push`/`flush`. The three existing release conditions
  are unchanged. `flush()` is idempotent, returns the text it emitted, and `speak()` calls it in the
  `finally` block **before** `tts?.endTurn()`, warning when it actually rescued something.
- **Not on a barge-in.** That text was correctly abandoned; speaking it after an interruption would
  talk over someone who just interrupted.
- **A malformed partial tag is flushed as-is and spoken.** Audible garbage beats silence — it is a
  model defect either way, and the version a human can hear is the version that gets reported.
- **`DEAD AIR on turn N`** — `console.error` when a turn produced text and TTS emitted zero audio
  bytes (barge-ins excluded). That condition was previously recorded only as a NULL, indistinguishable
  from the three benign causes of a NULL, which is exactly why ADR-100 mislabelled all ten rows.

Also surfaced by the same reconciliation and **deliberately not fixed**: the silence re-prompt fired
three times in call 25 alone, and on each one the caller answered within ~3s of being asked "Are you
still there?" The agent is interrupting people who are thinking. That is timer tuning on n=1 call.

## 2026-08-12 — Measured the voice pipeline, then fixed only what was free (ADR-100)

44 turns in production have a complete voice-to-voice measurement. `v2v` p50 **1863ms**, p90 4180,
p95 4394, max 8173. `pickup_to_first_audio_ms` 1770–2588ms on all 11 calls. Decomposing one turn
(call 25, turn 18): pre-LLM 129ms (8%) | **LLM TTFT 1136ms (71%)** | TTS 336ms (21%).

Two readings of this data corrected before acting on them:

- **Not geographically poisoned.** `voiceToVoiceMs` is `speech_final` → first TTS byte, server-side.
  The US-number→India-number leg inflates what the tester heard, not what the table recorded.
- **`tts_first_byte_ms` is cumulative from turn start**, not the TTS stage alone. Reading it as a
  stage duration overstates TTS and understates the model.

Shipped — four things, none of them "use a faster model":

- **Caller-transcript INSERT off the hot path.** It was `await`ed between STT `speech_final` and the
  LLM request, cross-region in prod (Railway Singapore → Supabase ap-south-1), writing a table the
  model never reads (it is fed from the in-memory `history` array). Now **chained** through a single
  `transcriptWriteChain` — not fire-and-forget: rows are read back ordered by identity column, so
  racing inserts would store a turn's agent line before the caller line it replies to. `finalizeCall`
  drains it behind `Promise.race([chain, sleep(2000)])`, so a call ended by `hangUp` or a mid-sentence
  hangup keeps the lines that explain why.
- **The literal-greeting fallback is no longer silent.** It has rejected **11 of 11 calls ever
  placed**, so every call paid ~1.3s of LLM TTFT for an authored sentence. Root cause is data — 3 of 4
  `leads` rows have `name = NULL` and `fields = {}`, so `{{lead_name}}` cannot resolve. Now warns with
  the unresolved tag names and the call SID. This is a diagnostic; ADR-094's authored tagless
  alternate line is still unbuilt.
- **Merchant free text trimmed at the render site.** Prod holds `org_agent_configs.name = "alice "`,
  which renders "This is alice  calling from …" and can be voiced as an audible stumble. Trimmed where
  it becomes speech, not on write — the bad rows already exist. No prod data was mutated.
- **`{{interaction_type}}` gets a producer** (insurance intake field + `interaction_type` /
  `interaction` CSV aliases). Same defect ADR-087 fixed for `interest_area`: the tag is in the NPS
  opener and its audited hi/hinglish translations, and nothing in `packages/api/src` could supply a
  value. Rewording the line was rejected — that is a compliance review, not a latency fix.

Deferred as unearned: the LLM TTFT fat tail (p50 1376 → p95 3826; needs per-request gateway-vs-model
timing first), the 10 of 78 turns that reserved a turn index and recorded no TTS first byte, and
Cartesia-vs-ElevenLabs first-byte at n=2.

  resolver that refuses a call already ringing is not a fix.
- **Inbound to a paused agent keeps answering on the default persona — now decided, not
  inherited.** `enabled` is an outbound gate only; `stream.ts` deliberately doesn't consult it, and

## 2026-08-09 — eight of the last seventeen ADRs were the same bug, and nothing here could see it

Prepping the first outbound pilot turned into a run of fixes that individually looked
unrelated and collectively were one thing.

**The pilot-scope decision came first.** The prospect's script has the agent read back a
routing number and take a voice-signature ACH authorization. That is the licensed act, and an
AI performing it is the unlicensed agent — the exposure is the operator's licence, not a
disclaimer. So the boundary became the product: the agent qualifies against nine permitted
pre-qual fields and warm-transfers to a licensed advisor with a pre-filled brief. It may not
claim licensure, recommend a carrier, quote premiums, itemize health conditions, collect
SSN/DOB/routing/account numbers, set an effective date or beneficiary, or take that
authorization. ADR-081.

**Then five voice/leads defects, each found by reading rather than by a test.**
`transferToHuman` was racing a concurrent `hangUp` instead of outranking it (ADR-082). TTS
connected eagerly, so a socket nobody had spoken on looked like a dead provider, tripped
failover and burned the call's sticky voice identity — now it connects lazily on first text
(ADR-083). Call health reported `healthy` for calls the caller was never heard in, because it
measured whether the pipeline threw rather than whether anyone spoke; it now counts
`callerTranscriptCount` (ADR-084). The outbound opener couldn't name who it had called —
lead greeting context is now resolved inside the pickup `Promise.all` (ADR-085) — and the two
merge tags that opener needs, `interest_area` and `state`, existed in no ingest path at all,
so they could never have been filled (ADR-087, amending ADR-085). A bespoke template written
for one account was seeded visible to every org in its vertical; `agentTemplates` gained
`visibility` + `ownerOrgId` and an admin grant route, with `seed.ts`'s update path
deliberately not touching either column so a grant survives re-seed (ADR-086).

**The prohibited-capture guard had zero callers.** It was written, documented and unit-tested
in the same session it was found dead. Now enforced at the write path in two layers:
`captureField.execute` refuses and tells the model why, and `logToolCall` redacts before
*both* the `tool_calls` insert and the outbound webhook, so a refusal logs a
`guardrail_event` carrying the field key and never the value. Twelve more keys added
(Aadhaar, PAN, passport, IBAN, IFSC, CVV, card and licence numbers) and the tool description
stopped advertising "account number" as something it accepts. ADR-088.

**CSV import ships preview-first.** `POST /api/leads/ingest/csv` defaults to `dryRun: true`
— only the literal string `"false"` writes — and the preview reports per-column
kind/target/alias/samples, regulated columns named but never sampled, dropped unknown
columns, and row issues by spreadsheet line number. Bare national numbers are refused unless
a `defaultCountryCode` is supplied. Building it surfaced that `validateFields` *coerces*
out-of-options enum values rather than dropping them, which is why there's a `warnings`
channel separate from blocking `errors`. The alternative was discovering all of this on a
live call to a real prospect. ADR-089.

**The pattern is the actual finding.** ADR-073 (`syncNumberWebhooksForOrg`, zero callers) and
ADR-088 (`findProhibitedCapture`, zero callers) are the identical defect found *three days

## 2026-08-09 — the follow-up was to add an owner check; the finding was that the two we have can't fire

ADR-079 shipped with one item left open: `POST /api/app/telephony/reset` had no owner-only check

`(user, org)`. One membership per user, in the database. The single insert site in the whole API
hardcodes `role: "owner"`, the column default is `"owner"`, and no invite path exists anywhere.
Production says the same thing: four orgs, four members, `owner | 4`. And `requireUserOrg` already
403s before any handler body runs, so `userRole` inside a route is never null and never anything
but `"owner"`.

So `/org/close`'s `if (userRole !== "owner") return 403` cannot fire, and `settings.tsx`'s
`isOwner` gate on the danger zone is always true. Copying that check onto `/telephony/reset` would
have added a third line that reads as access control, can never execute its deny branch, and would
tell the next person — reasoning perfectly well from three consistent examples — that this codebase
enforces roles. It doesn't. That is worse than the honest absence, because it is the sort of thing
a security review counts rather than tests. Same family as ADR-075's `ci-success` asserting what
failed instead of what succeeded: present in the source, absent in behaviour, trusted because
present.

Worth owning that ADR-079 made this worse before it made it better — the comment it added above
`/telephony/reset` said the route was reachable by "any member". There is no member who isn't the
owner. That sentence overstated the threat model in the same commit that fixed the real defect.

**The useful finding was underneath.** Enabling the role model is not a matter of writing checks;
they're already written. It means dropping `org_members_user_idx` — and that index is the audit#03
P1 fix, load-bearing for first-login race-safety. `resolveOrCreateMembership` mints
`org_${randomUUID()}` *before* inserting, so two concurrent first logins never collide on a
composite key; only the standalone unique index on the user rejects the loser and lets the
re-select converge. Drop it for invites and the same user's two in-flight first requests each
create a workspace. Silently, on the one path every new user takes, discovered in production.
Team invites therefore cost: drop the index, replace the race-safety with something else, *then*
the existing checks start meaning something.

The docstring on `resolveOrCreateMembership` had also drifted — it credited "the unique (user, org)
index", which is exactly the constraint the schema comment says would *not* catch the race. Two
files disagreeing about which constraint provides the guarantee is how the index gets dropped by
someone who read only one of them. Corrected to name the standalone index.

Nothing executable changed. `/telephony/reset` stays ungated on purpose and now says why; the two
inert checks are kept as the landing spot for invites and labelled as inert; `org_members.role` is
documented as a Phase 2 placeholder and deliberately left without a CHECK constraint, unlike
`platform_admins.role`, whose five-value vocabulary was already known and this one's isn't. Full
verification chain re-run to prove the diff is inert. ADR-080.

One thing found and not fixed: the losing racer in `resolveOrCreateMembership` can leave an orphan
`orgs` row — its `insert(orgs)` succeeds while `insert(orgMembers)` hits `onConflictDoNothing`.
Production has zero of them, so it has never fired; it's an empty row, and the invite work will
force that transaction open anyway.


## 2026-08-08 — the cleanup SQL was a symptom: admin could spend but not refund, and "reset" stranded what it paid for

Undoing this morning's Twilio provisioning experiment took hand-written SQL against
production. That got filed as an inconvenience. It was not — it was the only remaining
way to undo a purchase, and two structural defects in the telephony surface put it there.

**The admin panel could buy a number and never give it back.**
`POST /api/voice/orgs/:orgId/twilio/number` rents a number, monthly, and audit-logs it as
`twilio.number.purchased`. There was no admin release route. Release lived only at
`POST /api/app/numbers/:id/release`, behind a merchant session — which an operator does not
hold for someone else's workspace, and should not need in order to undo their own action.
The comment above `GET /orgs/:orgId/numbers` claimed the omission was on purpose
("buying/releasing numbers stays a merchant-side action"), and that was already false when
it was written: the purchase route is seventy lines up, in the same file. So the stated
design survived on the release half only. If exactly one of the two halves belongs on the
admin surface, it is not the one that bills every month. The inverse route now sits next to
its purchase: `POST /orgs/:orgId/twilio/numbers/:id/release`, admin-key gated, 400 on a
non-integer id before it touches Twilio, and it audit-logs `twilio.number.released` with the
**phone number** rather than the row id — `ReleaseNumberResult` was widened to carry it.
Months from now, "which number did we give up" is the only useful form of that record, and it
makes the trail symmetric with the purchase.

**The worse one was reachable by any merchant, not just an operator.**
`resetToPlatformDefault` nulls the org's Twilio SID and auth token and purges the telephony
vault, while `org_phone_numbers` rows stay `active`. `releaseNumberForOrg` resolves its Twilio
client from exactly those credentials. So after a reset the number is still rented, still
billing, our DB still says it is active — and **no route in the system can release it**, merchant
or admin, because the credentials needed to reach the sub-account were just deleted.
`syncNumberWebhooksForOrg` can't see it either, for the same reason. Recovery means digging the
sub-account SID out of the audit log or the Twilio console and writing SQL by hand. Which is
what happened.

That behaviour had a written justification: don't delete provider-side resources, "that's a
deliberate manual action on the provider's own console." Sound for BYO. False for platform mode
— and this repo already documents why, two docstrings away, where `inboundVoiceWebhooks`
explains that a platform-mode merchant's number "lives in a sub-account under Weeber's parent
account, so they have no console login for it." Two docstrings in one file, each correct alone,
pointing at an escape hatch that does not exist for the case that costs money.

`resetToPlatformDefault` now returns a result instead of `void`. When the org is not BYO and
holds any active number, it refuses — names the blocking numbers, and **writes nothing**: no org
update, no vault purge. Both callers surface it as 409, because the request is well-formed and
the workspace state is the blocker. The load-bearing test is the one asserting it writes nothing
at all when it refuses; a guard that refuses *after* clearing the credentials would produce the
exact unrecoverable state this fix exists to remove.

Three calls worth pinning. **Refuse, don't auto-release** — a button labelled "revert to platform
default" must not silently destroy paid, dialable, possibly-advertised numbers, and Twilio will
not hand the same number back. That mirrors what `getSubClientEnsuring` already argues: creating
a sub-account is implicit because it's free, "the *number* is the chargeable step, and that stays
an explicit user action." Releasing is that step in reverse. **Anything not explicitly `"byo"` is
platform-owned** — unknown org, null mode, both fall in the guarded branch, because guessing BYO
is the expensive way to be wrong. **BYO passes through unchanged.**

The refusal also has to be legible. `integrations.tsx`'s reset mutation threw a hardcoded
"Failed to reset telephony settings" and discarded the response body — the one mutation in that
file not following its own `data.error ?? fallback` pattern. A guard whose explanation is
swallowed on the way to the toast is the dead end ADR-073 was written about. It now shows the
server's message, so the merchant is told which numbers to release first.

**One correction.** Triage recorded `closeOrgTelephony` as having zero callers — the same shape
ADR-073 found in `syncNumberWebhooksForOrg`. That was wrong. It has three live callers
(`POST /api/app/org/close`, plus the 30-day suspend and 60-day close in the org lifecycle sweep),
and the sweep is wired into the scheduler. Written down here because the false claim was written
down first, and a stale "this is dead" note is how live code gets deleted later.

Ten new tests, both files proven to fail without the fix (4/5 with 404s for the route, 5/5 for the
guard). Green: lint 0/0 across 467 files, api 966 pass, web 74 pass, e2e 2 passed, visual 78 passed
with zero baseline changes — confirming the `integrations.tsx` edit changes no pixels.

Still open: `POST /api/app/telephony/reset` has no owner-only check, unlike `/org/close`. The guard
removed the expensive consequence, not the permission gap. See ADR-079.

## 2026-08-08 — every number we ever bought was inert, and the purchase path said "ok"

Both numbers this platform has ever purchased came back from Twilio with no
`voice_url` and no `status_callback`. An inbound call to either one hit Twilio's
default "not in service" message and no webhook ever reached us — they rang and
dropped. `buyNumberForOrg` reported success for both, because its only check was
that `incomingPhoneNumbers.create` didn't throw.

Both were repaired by hand through the admin `sync-webhooks` route, each on the
first try: `{"checked":1,"repaired":["+1…861"]}` and `{"checked":1,"repaired":["+1…413"]}`.

The cause of the drop is **not proven**, and everything on our side was ruled out
by command. `git show 439650a:…/twilio-provisioning.ts` proves the deployed build
contained the create call with the webhooks in it; `rg` finds exactly one create
and one `insert(orgPhoneNumbers)` in the whole codebase, so both purchases went
through it; driving the real `twilio@6.0.2` client through a recording `httpClient`
shows all five params (`PhoneNumber`, `VoiceUrl`, `VoiceMethod`, `StatusCallback`,
`StatusCallbackMethod`) on the wire; and `voiceApplicationSid`/`trunkSid` — the
only documented reason Twilio ignores `voice_url` on create — are unset on every
number in the fleet. The two purchases ran on two different builds, in two
different Twilio accounts, three days apart, with the same result.

Twilio's own Monitor audit trail is what closed the question of where it went:
each `phone-number.created` event lists `voice_method` and
`status_callback_method` but **no `voice_url` and no `status_callback` at all**,
and the repair event records `voice_url: {previous: None}`. The fields were never
set, not set and lost.

So the purchase path stops inferring configuration from the absence of an
exception. It reads `voiceUrl`/`statusCallback` back off the create response,
re-applies them with an `update` when they disagree, and re-checks that response
too. The `org_phone_numbers` row is written **even when that fails** — the org is
billed from the moment `create` returned, and a number missing from that table is
invisible to `syncNumberWebhooksForOrg`, which is exactly how the platform's
legacy `TWILIO_PHONE_NUMBER` number ended up with a dead `trycloudflare.com`
webhook nothing can reach. The failure then returns an error naming the real
state: bought, recorded, billable, will not answer calls.

`remoteMatchesWebhooks` is now the shared definition of "correctly configured"
for both the purchase and sync paths, and it compares `statusCallback` as well as
`voiceUrl`. Sync previously compared `voiceUrl` alone, so a number that answered
calls but silently dropped every completion event — no duration, no status, no
cost — counted as healthy.

The old test suite could not have caught any of this: it mocks the `twilio` module
wholesale and asserts the arguments we pass it, which is blind to a param lost
between the SDK and the HTTPS request. `twilio-purchase-webhook-wire.test.ts`
drives the real SDK through a recording `httpClient` and asserts the serialised
request body instead. It imports the client by its deep CJS path because sibling
files' `mock.module("twilio")` calls are process-wide and would otherwise hand it
a mock. Four behavioural cases cover the read-back; two of them fail with the
source change stashed.

ADR-077.

**Update, same evening — the root cause is now bounded, and it is not our code.**
One number was bought on the fixed build into the same sub-account that failed on
Aug 5, then released immediately (HTTP 204). It **worked**: the create event
carries both `voice_url` and `status_callback`, and there is no follow-up
`phone-number.updated`, so `create` set them itself and the new verify step had

The discriminator is the egress IP Twilio recorded on each create: both failures

The read-back therefore stays as a safety net rather than a fix for a live bug.
The experiment also left two prod rows needing correction by hand (the throwaway

## 2026-08-08 — the deploy that crash-looped without saying why

`1de740a` has been green in CI since it landed and took five attempts across 35
minutes to reach production — four failed, one succeeded 58 seconds after a
failure of the identical commit with nothing changed in between. Railway reported
"1/1 replicas never became healthy", which was a symptom: the container was
crash-looping every ~1.5s because `bunx drizzle-kit migrate` — the first half of
`start:railway` — exited 1 before the server could bind.

The deploy log contained no error. Not a truncated one: the raw log stream was
re-fetched and decoded with carriage returns expanded and ANSI stripped, and the
Postgres error is not in the stream at all. drizzle-kit clears its spinner line
on failure and exits without printing what the database said.

Everything testable from outside the container checks out. Production has all 47
migrations applied with nothing pending; the same 47-row state was replayed
against a throwaway local database and `drizzle-kit migrate` succeeded; the
drizzle-kit version matches the lockfile; the database has 15 of 90 connections
in use, is not in recovery, and is 14 MB; and the port-6543 pooler passed a
96-query probe across 8 connections with prepared statements both on and off.
Same commit, same URL, same state — fine from a sandbox, intermittently dead in
the container. **The root cause is not proven.**

Two real intermittency sources did turn up. First, `main` deploys to staging
*and* production at once: the two `repoTriggers` are not duplicates, they are one
per environment, and on the 17:34 push staging was created 385ms before
production, succeeded, and production failed. Staging shares production's
`DATABASE_URL`, so both containers ran migrations against one database inside the
same second — and `CREATE SCHEMA IF NOT EXISTS` is not concurrency-safe, the
loser of that race gets a unique violation rather than a silent skip. Second, a
session-level `SET default_transaction_read_only` had leaked onto a pooled
Supavisor backend earlier the same day (staging's seed hit `cannot execute UPDATE
in a read-only transaction`); a migration handed that backend dies on its first
DDL statement, and which backend you get is luck. Those backends have been reset
and 6 distinct ones now verify `off`.

So the first fix is to stop flying blind. Production migrations now run through
`packages/api/scripts/migrate.ts`, using drizzle-orm's own migrator against the
same journal and the same `drizzle.__drizzle_migrations` ledger — migration
history is unchanged and still shared with `bun run db:migrate` locally. On
failure it prints every field Postgres populates and then walks `.cause`,
because drizzle-orm puts the failing SQL on the outer error and the real
`PostgresError` one level down.

Two things this also corrects on the way past: production was booting by
invoking a **devDependency** CLI through `bunx`, and that CLI builds its own
postgres.js client with prepared statements **on**, which contradicts the
`prepare: false` the app's own client has documented as required for Supabase's
transaction-mode pooler since ADR-034.

Result: `ac49d35` deployed to production at 18:26 and again on a redeploy at
18:29 — two consecutive successes against four failures out of five on the old
command — and the container now logs `[migrate] up to date in 622ms` instead of a
spinner.

Both deployment triggers were also switched to `checkSuites: true`. They were
`false`, meaning ADR-075's gate protected `main` but protected nothing about what
reached production; a red check suite can no longer auto-deploy.

Migrations still run in the start path, so a failure still crash-loops rather
than blocking the deploy. Moving them to Railway's `preDeployCommand` is next and
deliberately not bundled here. Also still open: staging and production share one
database, so a staging deploy carrying migrations production lacks would apply
them to production's schema — both triggers watch `main` today, but nothing
enforces that.

See ADR-076.

## 2026-08-06 — The agent hung up on a caller who was answering

Two rows in production `transcripts`, 38 milliseconds apart, on call 16:

```
16:16:22.239  caller  "Yes."
16:16:22.277  agent   "I haven't heard back, so I'll go ahead and end the call here. Goodbye."
```

The caller answered. The agent said goodbye anyway and hung up.

The silence machinery re-prompts after 8s of quiet and hangs up 7s after that. The STT handler cancels
it with `clearSilenceTimer()` the moment the caller speaks — which works right up until the timer has
already fired. At that point `handleSilenceTimeout` is running and suspended inside
`await speakCannedLine(...)`: flags read, TTS cache checked, a full spoken turn synthesized and sent.
Clearing an elapsed timer cancels none of that. The decision to hang up was made before the await and
executed after it, with nothing re-checked in between. Everything the caller said inside that window
was written to the transcript and then ignored.

The window is however long it takes to speak a sentence, and it opens on **every** silence timeout.

Two obvious fixes don't work, both for the same reason: `speak()` re-arms the silence timer on its own
tail, so the canned line spoken *by* the timeout re-arms the timer itself. A post-await
`silenceTimer === null` check always sees a live timer; a timer-generation counter always sees a bumped
generation and would abort every hangup, including the correct ones.

So the cancel signal is caller speech, not timer state: a `callerSpeechEpoch` counter, bumped where the
STT handler consumes a real end-of-turn, captured when the timer is armed, and re-checked after every
await inside the timeout. If it moved, the timeout abandons itself. The line already spoken can't be
taken back; the hangup doesn't happen.

Only that one site bumps the epoch. Barge-in deliberately does not: aborting a timeout leaves no timer
armed, and with no max-call-duration cap anywhere in the stack, that timer is the only thing preventing
a call that stays open forever. The end-of-turn site is safe because every path below it re-arms;
barge-in fires on interim text that may never produce a `speechFinal`. Trading a wrong hangup for an
immortal call is not a trade worth making, so the narrower fix stands and the residual gap is written
down rather than papered over — see ADR-074.

Two tests, both driving the real state machine with fake timers: the caller who answers mid-goodbye
stays connected (fails against the pre-fix code), and the caller who is genuinely silent still gets
warned and then hung up (so the race can't be "fixed" by quietly disabling the feature).

## 2026-08-05 — The Hindi agent could not hear anyone

Reported defect: the Hindi agent is not listening. Two unrelated root causes, one per STT provider, both
ending in a call that stays up and transcribes nothing.

Reproduced without a phone call: Sarvam TTS synthesized the Hinglish sentence from the July Hindi work at
8kHz mu-law, and it was streamed through the real adapters in 160-byte/20ms frames at real-time pace —
Twilio's exact wire format and cadence — then followed by mu-law silence, because a real stream never stops
sending and endpointing depends on that. Before the fix: **Sarvam heard nothing at all** on both `hi` and
`hinglish`, and **Deepgram never even connected** on `hinglish`.

**Sarvam was sent a wire format it silently refuses.** The adapter declared `input_audio_codec=pcm_s16le`
at connection time, then wrapped every single 20ms frame in a 44-byte RIFF/WAVE header — ~12% of each
message. Sarvam returned no transcript *and no error*. Four combinations were tested against the real
endpoint: WAV-per-frame is silent whether the codec is declared `pcm_s16le` or `wav`; raw PCM with the
per-frame `sample_rate`/`encoding` fields dropped is rejected outright (`audio.encoding Field required`);
raw PCM **with** those fields still present transcribes correctly. So `encoding: "audio/wav"` is a required
field whose value is ignored, sitting next to bare PCM16LE bytes — which is also the one shape Sarvam's own
spec calls illegal, since it marks both fields required while stating 8kHz is connection-parameter-only.
Read the docs and the natural fix is the only combination that fails.

The July "live-verified Sarvam" note wasn't wrong, it was under-powered: that test streamed large buffers,
where one header per multi-second chunk is noise. The bug only exists at Twilio's frame size.

**Deepgram was sent a language code that stops the socket from opening.** Any non-English language was
forwarded verbatim. Live handshakes against nova-3: `hi`, `mr`, `ta`, `te`, `kn`, `bn`, `gu`, `pa` and
`multi` return 101 — `hinglish`, `ml` and `hi-IN` return 400. Both `hinglish` and `ml` ship in the agent
config dropdown. A 400 means three wasted reconnects and then a deaf call for its whole duration. This also
corrects the module's own comment, which implied every Indian language in our list worked.

**`hinglish` never had a Sarvam code either.** `toSarvamLanguageCode` built `${language}-IN` blindly and
produced `hinglish-IN`; Sarvam accepts the socket, then rejects the request and closes. Two comments — in
this adapter and in `agent-frame.ts` — claimed it mapped to `hi-IN`. Only the TTS adapter actually did it.

**And a deaf provider reported itself healthy.** Sarvam `error` messages were a bare `console.error`. STT
failover was already built and wired; it was simply never told, so a rejected stream produced a call that
kept billing LLM and TTS while unable to hear a word. Errors now escalate to `onFatalError` and the
failover chain engages.

Also: Sarvam takes ~900ms–1.2s to connect versus Deepgram's ~130ms, and `sendAudio` dropped every frame
until the socket opened — clipping whatever the caller said first. It now holds a bounded 2s tail and
flushes on open, the same way the Deepgram adapter already handled reconnects.

After the fix all five configurations transcribe and produce turn-finals, with English words in Latin
script and Hindi in Devanagari — the `codemix` behaviour the July work intended but could never deliver
while the audio wasn't arriving. Still unverified on a live PSTN call; the audio path tested is
byte-identical to Twilio's, but the first real Hindi call should still be watched. See ADR-072.

## 2026-08-05 — The agent said goodbye and the call stayed up

Reported defect: the call is not ending. Four causes, all of them a step in the teardown sequence being
skipped without an error anyone would connect to hangups.

**A hangup could throw before it closed the socket.** `performHangUp` ended the Twilio leg as one
expression — `await (await getTwilioClientForOrg(orgId)).calls(sid).update({...}).catch(log)` — where the
`.catch` covers `update()` and nothing before it. `getTwilioClientForOrg` does a DB + credential-vault
read and then constructs `Twilio(sid, token)`, which throws on a malformed SID: exactly the
half-provisioned sub-account state `twilio-provisioning.ts` documents. The whole function then rejected,
so `ws.close()` and `finalizeCall()` never ran — and closing the socket is what actually ends a
`<Connect><Stream>` call. It surfaced as a generic `[voice] error handling transcript event`, which names
neither hangups nor Twilio.

**A hangUp with no `reason` was discarded.** `logToolCall` gated the intent on `"reason" in input`.
`reason` is required on the schema, but a model can emit `{}` and an SDK can hand back arguments that
never parsed into an object. The caller heard the goodbye line the same turn produced, then sat on a live
call.

**A failed transfer left a zombie leg.** `performTransfer` called `finalizeCall("transferred")` whether or
not the redirect worked. Finalize closes STT/TTS and clears the silence timer while `performTransfer`
deliberately leaves the socket open — so a failed redirect meant a live call with no agent listening,
nothing left to end it, and a call record claiming a transfer that never happened.

**The browser test call ignored both call-control tools.** `test-call-stream.ts` captioned
`[tool: hangUp]` into the transcript and did nothing. `buildVoiceTools` always re-adds `hangUp`, so every
preview agent has it and uses it — and the preview call kept the mic open and kept billing STT/LLM/TTS to
the 5-minute cap. That is the surface a merchant tests first.

**Fixed** (ADR-071): closing the WebSocket is the authoritative end of a call; the provider REST hangup is
best-effort and **cannot throw**. New `endProviderCallLeg()` wraps client construction and provider
dispatch, so `performHangUp` always reaches `ws.close()` + `finalizeCall()`. The Twilio hangup retries
once, then logs loudly with the attributed org — its likeliest failure isn't transient, it's an
unattributed call resolving to the *parent* client while the call lives in an org sub-account, which 404s.
Call-control intent registers on the tool **name** alone via the shared `voice/call-control.ts`
`toolCallReason()`. A failed transfer hangs up instead of reporting success. The test call honours both
tools, waiting (bounded) for the closing line first, and *reports* a transfer rather than pretending a
handoff happened.

`stream-hangup.test.ts` drives the real stream state machine: three of its tests fail without this change
(argument-less hangUp, Twilio client construction throwing, failed transfer redirect) and the
healthy-transfer control passes either way.

## 2026-08-05 — The agent's voice could change mid-call, then change back

Reported defect: the voice changes during the call. Three causes, all in the per-turn cross-provider
TTS failover path (`voice/stream.ts`), none of them visible in a log or on the call record.

**The configured voice ID was handed to the fallback provider.** `attemptTts` passed
`ttsVoiceIdOverride` unchanged on every failover hop. Voice IDs are provider-scoped — a Cartesia UUID,
an ElevenLabs ID interpolated into the WebSocket URL *path*, a Sarvam *speaker name* — and every
adapter fails open on a foreign one (`voiceIdOverride || process.env.<PROVIDER>_VOICE_ID`, Sarvam then
falling back again to `DEFAULT_SPEAKER = "shubh"`). So the fallback either killed the turn or spoke in
an env-default voice nobody chose.

**A failover was undone on the next turn.** The chain was rebuilt from the configured primary inside
`speak()`, every turn. One transient error therefore made turn *N* speak in the fallback's voice and
turn *N+1* flip straight back — the agent audibly became a different person and then changed back.

**The cache learned the wrong voice.** `tts-cache` is process-global and keyed on
`(provider, voiceId, language, text)`, but all four call sites computed that key from the *intended*
provider before synthesis. Audio a fallback produced was stored under the primary's key, so canned/
filler/backchannel lines replayed in a mismatched voice — for the rest of that call and every later
call in the same process.

**Fixed** (ADR-070): new pure `voice/tts-voice-identity.ts` (`voiceIdForProvider`) — a voice ID only
ever reaches the provider it belongs to, and a fallback uses its own default voice instead.
`activeTtsProvider` makes a failover **sticky for the rest of the call**, so the voice changes at most
once instead of per turn. All tts-cache reads/writes go through one `currentTtsVoice()` helper, re-read
*after* speaking on the canned-line path so a line that itself failed over is stored under the provider
that produced it.

**Also:** `calls.ttsProviderUsed` and the per-call cost estimate read the configured override, so
ADR-060's smart Indic default recorded `null` and a mid-call failover left no trace — this defect could
not have been confirmed from the call record. Both now report the provider that actually spoke. And the
Preview drawer's "simulate provider failure" toggle carried the primary's voice ID onto the fallback
(same bug, and it resolved the primary *without* the call's language, so an Indic agent was shown a
chain the real call would never take).

## 2026-08-01 — The model was choosing whose CRM record a call wrote to

`crmSync` declared `phoneNumber: z.string()` as a **required, model-authored input**
(`voice/tools/crmSync.ts:15`), and that same string was the **upsert key**: `syncToGoHighLevel` POSTs
it as `phone` to `/contacts/upsert` (`integrations/gohighlevel.ts:23-32`). GoHighLevel matches on
phone, so a wrong number does not fail — it **silently writes this call's notes onto a different
person's contact record** in the merchant's live CRM, or creates a junk one.

Three routes to a wrong number, none of them exotic. (1) The LLM hallucinates digits — it was being
asked to emit a value no layer of the prompt ever gives it, which is the exact condition that
produces invention. (2) STT mangles a number the caller reads aloud; digit errors are the single most
common Deepgram/Sarvam failure mode on Indian accents and there was no confirmation step. (3) A
caller simply says a number that isn't theirs — the tool had no way to disagree.

And the correct value was already sitting three frames up the stack. `resolveHumanNumber` produces
`humanNumber` in the `"start"` handler (`voice/stream.ts:1561`) from the carrier's signalling. The
codebase already trusts it for two consequential things: DNC opt-out matching (`:515`) and caller
memory lookup (`:611`). Only the CRM write took the model's word instead.

**Fixed** (ADR-069), same pattern as ADR-064/066: `CrmSyncContext = { orgId, phoneNumber }`,
`resolveCrmSyncContext()`, `createCrmSyncTool(ctx)`, resolved once at `"start"`
(`stream.ts:1580`) and fixed for the life of the call. Model input narrows to
`{ callerName?, notes }` — `phoneNumber` is **gone from the JSON Schema**, not merely ignored.
Optional-with-a-default was rejected: a field in the schema is a field the model will fill.

**Non-registration is the gate.** `crmSync` was removed from the static `voiceTools` map in
`agent.ts`; `buildVoiceTools` takes a 6th `crmSync?: CrmSyncContext` and only registers the tool when
that context resolved. No caller number → the tool does not exist on that call, and the model is
never told about a capability that would fail.

**Intended side effect, stated rather than buried:** the text test-chat, the synthetic harness and
the preview drawer now get **no** `crmSync`, because none of them has a carrier-supplied number. That
is a fix. A test conversation could previously write a live contact into a merchant's production CRM.

**Also:** five seeded insurance personas documented the old signature in their tool tables
(`` crmSync({ phoneNumber, notes }) `` → `` crmSync({ notes }) `` in `docs/agent-prompts/0{4,5,6,7,9}`).
Those markdown files *are* the shipped system prompts — `seedAgentTemplates` reads them — so a stale
tool table teaches the model an argument that no longer exists.

**Verified:** api tsc 0 · web tsc 0 · api 852 pass / 0 fail (2213 expects, 101 files, `--isolate`) ·
web 74 pass · oxlint 0/0 (414 files). 13 new tests: the schema exposes exactly
`["callerName","notes"]`; a model-supplied `phoneNumber` loses to the bound one; five
`resolveCrmSyncContext` cases; six registration-gate cases including "`toolsEnabled` alone is not
sufficient" and "absent from the static map".

**Not verified:** no live call. The specific open question is whether `humanNumber` is populated at
`"start"` for **every** telephony provider — Exotel's WS-only path inserts the `calls` row later than
Twilio/Plivo. Failure mode there is a *missing* CRM write, not a wrong one, which is the right way
round. It is Step 7 of the new call-test protocol.

## 2026-08-01 — The sidebar took 224px and nothing in the layout knew

`/app/integrations` at a 768px viewport rendered **"Not connected" one letter per line**, as vertical

## 2026-08-01 — Phase III verified in a browser, and it immediately found two defects

Closes the gap the Phase III entry below states in its own last line: *"nothing was viewed in a running
browser — no dev server booted."* Now it has been, and the render was not clean.

**Defect 1 — the call-control block has shipped ragged indentation on every call ever placed.**
`buildCallControlBlock` (`voice/agent.ts:220`) returned a ``dedent`…` `` template. `dedent` computes the
minimum indentation of the **interpolated** result, and most of the interpolated values (`transferLine`,
`numbersLine`, `indianFormatLine`, `identityCheckLine`, `unauthorizedPromiseLine`) are multi-line
constants whose continuation lines are flush-left. So the minimum was always 0, nothing was ever
stripped, and the model received a block where the literal lines carried the source file's 6-space indent
and the interpolated ones carried none. Fixed by assembling a flush-left `string[]` and joining on `\n`;
`dedent` is still used for the four single-line-interpolation templates (`agent.ts:41`, `:909`, `:943`,
`:964`) where it works correctly. **Prompt content is unchanged — only leading whitespace differs.** New
regression test loops `inbound`/`outbound` and asserts no line in the `call-control` segment matches
`/^ {3,}/`. The `segments.map(s => s.body).join("") === text` invariant still holds byte for byte.

Worth naming plainly: this was invisible for the life of the product and no test could have caught it,
because no test read the prompt as a human reads it. It surfaced within minutes of the D2 panel rendering
the block on screen for the first time. That is the entire argument for [ADR-067](../decisions/adr-067-one-composition-path-and-a-compiled-prompt-panel-the-editor-shows-what-ships.md),

near-white text on a pale background in the light theme, i.e. an invisible warning in the mode most
merchants will use. Converted to the semantic `warning` / `foreground` tokens already used at
`agents.tsx:515`, per `UI-DESIGN-BRIEF.md`'s rule against raw Tailwind colour scales in product routes.

**How it was verified.** `ToolsGuardrailsTab` is now exported (DEV harness only, documented at the

`looksLikePromptInjection` was nine English regexes, every one of them shaped
`verb ... object` (`/ignore\s+(all|your|the|any)?\s*(previous|prior|above)?\s*instructions?/i`). Two
reasons that could never fire on the calls this product is built to place:

1. **Hindi and Hinglish are SOV — the verb lands last.** "saare instructions bhool jao", "अपने सारे निर्देश
   भूल जाओ". No amount of synonym-stuffing makes a verb-then-object pattern match a verb-final sentence.
2. **Romanized Hinglish has no fixed spelling.** bhool / bhul / bhuul, nazarandaz / nazrandaz /
   najarandaj. Enumerating literal phrases is unwinnable.

So the fix is not "add more regexes". Extracted to `voice/injection-detection.ts` (re-exported from
`stream.ts`, same pattern `endsMidThought` already uses) and given four layers: the original English
phrases unchanged, **order-independent co-occurrence** of an override or disclosure verb stem within 45
characters of an instruction noun stem, authority claims (`main tumhara developer hoon`, `मैं तुम्हारा
डेवलपर हूँ`), and roleplay imperatives (`ban jao`, `बन जाओ`, `naatak karo`). Stems rather than whole words,
because `\b` is meaningless around Devanagari in JS regex and because Devanagari inflects by suffix — भूल
covers भूलो / भूलकर / भूल जाओ for free.

Two details that only showed up under test:

- **Nukta normalization.** नज़रअंदाज़ (precomposed ज़ U+095B) and नजरअंदाज (base ज) are the same word, and
  STT providers are not consistent about which they emit. `normalizeForInjectionCheck` decomposes, strips
  U+093C, recomposes. Pattern literals must therefore be written nukta-free (छोड, तोड, पढ) — writing छोड़
  in the pattern silently never matches normalized input.
- **A real false positive, caught before shipping.** Pairing disclosure verbs with a single noun set
  flagged *"batao ki return ka niyam kya hai"* — a customer asking about the return policy. `rule` /
  `niyam` / `नियम` are now excluded from the disclosure noun set and kept only for override pairing
  (telling an agent to forget its rules is an attack; asking what the rules are is not). Remaining accepted
  false positive, documented in the module: "main niyam bhool gaya" ("I forgot the rules").

Also fixed a pre-existing English gap while in here: `/i('m| am)\s+(the\s+|a\s+)?(developer|admin|administrator)\b/`
never matched **"I'm an administrator"** — `a\s+` can't consume "an". Now `an?\s+`.

Unchanged: this is **log-only**. `stream.ts:1411` records a `guardrail-heuristic-detector` tool call for
dashboard review and the turn proceeds exactly as before. Nothing is blocked, no caller is cut off, and the
model's own `flagGuardrailEvent` remains the primary path. 20 new tests covering all three scripts plus a
clean-conversation set in each.

## 2026-08-01 — Pilot gate G1.3/G1.4: seeded personas were templates nothing ever rendered

Every file in `docs/agent-prompts/` was written with merge tags — `{{merchant_name}}`, `{{cod_amount}}`,
`{{order_id}}`, `{{product_name}}` and more — and **nothing rendered them.** `seed.ts` loads each file
verbatim into `agentTemplates.defaultPersonaPrompt`; `resolveAgentConfig` assigns it raw. The only string
in the voice path that goes through `renderTemplate` is `literalGreetingTemplate`. The persona body, which
governs the whole call, reached the model with the braces still in it — one bad turn away from an agent
reading `{{cod_amount}}` aloud to a customer.

Rendering the persona was the obvious fix and was **rejected** (ADR-065): there are two tag vocabularies
that have drifted apart (`MERGE_TAGS` in `graph-types.ts:111-122` says `shop_name`/`cart_value`; the docs
say `merchant_name`/`cart_total`), and `cart_items_summary`, `product_name` and `delivery_days_estimate`
have **no producer anywhere in the codebase** — rendering could never have resolved exactly the tags that
matter.

**Values now travel as values.** Personas `01`, `02`, `03` rewritten tag-free, phrased as instructions
("what you are given is given to you as context; if a detail wasn't given, you don't have it"). Facts
arrive through blocks that emit a line **only when the fact is known**: `buildIdentityBlock` (now carries
`merchantName`, with `orgs.name` fetched in a `Promise.all` alongside the template in `resolveAgentConfig`),
`buildWorkflowContextBlock` → `buildWorkflowFactsBlock`, `buildKnownFactsBlock`, `buildCallerMemoryBlock`.
`buildWorkflowFactsBlock` had been written and unit-tested but **never called from the live path** — the
workflow metadata sat in the session and never reached a prompt. `stream.ts` now captures it call-scoped in
`"start"` and threads it into `runVoiceAgentTurn` (`:1240`) and `runVoiceAgentGreeting` (`:1297`).

**New: `voice/merge-tags.ts`.** `scrubSystemPrompt(prompt, label?)` runs on the *final composed* prompt at
the single `streamText({ system })` call site — one site covering live calls, text test-chat, the synthetic
harness and the preview drawer. Any surviving `{{tag}}` is **removed** (not substituted with `<unknown>`,
not guessed), whitespace repaired, tag names logged once. Custom personas a merchant types are covered too.

**New: `database/prompt-hygiene.test.ts`.** Per-template merge-tag check with a
`MERGE_TAG_MIGRATION_BACKLOG` for the six insurance personas that asserts the backlog **may only shrink**;
an `ENGINEERING_METADATA_PATTERNS` scan (source paths, `.ts` filenames, DB table refs, competitor names,
`Weeber`, dated internal notes, planning-doc refs); and an assertion that nothing in `notes/` is ever
seeded.

**G1.4 — engineering context split out.** The personas had been doubling as engineering docs: variable
tables naming DB columns, source paths, dated "known gap" asides, a competitor jab, and in one case a
*false* claim that the knowledge base doesn't exist (it does — `knowledgeDocuments`, `knowledgeChunks`,
`voice/knowledge-base.ts`). All of it moved to `docs/agent-prompts/notes/0{1,2,3}-*.notes.md`, which is
never seeded. Measured with `o200k_base`: `01` 2457 → 1954, `03` 1824 → 1569, `02` 1725 → **1814** (it grew
— it gained real guardrails). The saving is modest; the actual cost was instruction dilution and a persona
lying about the product's own capabilities.

**Three producer defects found while doing this, all silent:**

1. `buildWorkflowFactsBlock` required `cart_value` **and** `currency` together, and the COD producer
   (`integrations/shopify/routes.ts`, `orders/create`) never wrote `currency` — so the COD confirmation
   agent could not state the amount it exists to confirm. Fixed both sides: the producer now mirrors the
   abandoned-checkout context's `String(body.currency ?? "INR")`, and the block emits a bare amount with an
   explicit "currency unknown — say the number without naming a currency" qualifier as a backstop.
2. The facts block emitted **no order reference at all**. Producers write camelCase `orderId`; the block
   and the docs said `order_id`. Now reads `order_id ?? orderId`. **Do not rename `metadata.orderId`** —
   `voice/workflows/engine.ts:53` reads it for the post-call Shopify annotate.
3. `03`'s seeded `literalGreetingTemplate` contained `{{product_name}}`, which has no producer. `stream.ts`
   correctly refuses to speak a partially-rendered greeting, so the fast canned-greeting path **never fired
   once** for this agent and every feedback call silently paid full LLM time-to-first-token on its opening
   line. A seeded greeting tag with no producer is an invisible permanent latency regression. Removed.

**G1.3 also covers `confirmCodOrder`, which was worse than the discount tool ever was** — see ADR-066. It
took `{ shop, orderId, confirmed, notes }`, and `confirmed: false` cancels a Shopify order immediately and
irreversibly. Per defect 2 above, the model had **never been told the order reference**, so its only
options were to ask the customer to read it out or invent one — and a plausible invented integer cancels a
real, unrelated, in-flight order. Now `createConfirmCodOrderTool(ctx)` + `resolveCodOrderContext({ metadata })`
in `stream.ts`'s `"start"`; model input is exactly `{ confirmed, notes }`; bound values win if a model emits
`shop`/`orderId` anyway; removed from the static `voiceTools` map and registered only when the context
resolves (shop present, order id a safe positive integer) — so an inbound or cart-recovery call carries **no
cancel tool at all**. The persona layers a soft control on top: a cancellation needs the customer to refuse
twice, and an unsure customer becomes a callback.

Persona content changes worth knowing: `02` can no longer estimate a delivery time (the old
`{{delivery_days_estimate}}` fallback of "seven to ten" was a fabricated number the agent would have stated
as fact) and no longer names the product; `03` says "your recent order", never promises a refund,
replacement or callback time, and no longer offers to send a review link it cannot send.

Decisions recorded in
`../decisions/adr-065-values-not-placeholders-prompts-instruct-fact-blocks-supply-values.md` and
`../decisions/adr-066-a-tool-that-acts-on-a-real-world-entity-is-bound-to-that-entity-server-side.md`.
Verified: api tsc ✓ · web tsc ✓ · `bun test --isolate src/` 810 pass / 0 fail (up from 787, +23 tests).

## 2026-08-01 — Pilot gate G1.1: the merchant's discount, not the model's

First of the G1 pilot-blocking fixes from `../../audit/pilot-readiness-checklist-2026-08-01.md`.

`offerCartRecoveryDiscount` let the LLM fill in `percentOff` — `z.number().min(1).max(30).default(10)` —
so on a live call the model chose how much of the merchant's margin to give away, and silently issued 10%
whenever it named no number. Meanwhile the merchant's *actual* configured discount (flat or escalating per
attempt, `NodeConfigPanel.tsx:159-216` → `resolveDiscountPercent` at `graph-engine.ts:178` → persisted to
`scheduledCalls.metadata.discount_percent` at `graph-engine.ts:200`) was being ignored. `shop` and
`checkoutTokenOrOrderRef` were model-supplied too — a model-invented ref breaks retry-safety (the same
call retried must reproduce the same code), and a model-supplied `shop` is a cross-tenant write surface.

**The tool is now a factory bound from server-side call context.**
`createOfferCartRecoveryDiscountTool(ctx: CartRecoveryDiscountContext)` — same pattern as
`createLookupInfoTool`. `percentOff` / `shop` / `checkoutTokenOrOrderRef` / `prepaidOnly` are **removed
from the model-facing input schema** and closed over. The only remaining input is `reason` (the hesitation
the agent heard) — the one field the model is the right author of, it keeps the schema non-empty for
strict tool-calling providers, and it gives the merchant an audit trail on the call-detail timeline. The
tool description names the exact bound percentage so the agent can speak it accurately without choosing it.

**Non-registration is the enforcement.** `resolveCartRecoveryContext({ metadata, checkoutToken })` returns
`undefined` when the shop, the checkout ref, or a non-zero `discount_percent` is missing — and
`buildVoiceTools` then **does not register the tool for that call at all** (`agent.ts:718-719`, written as
two concrete object shapes; see the ADR for why a conditional spread breaks `TypedToolCall` inference).
Not registered-at-0%, not an org-default fallback. A tool that isn't in the request can't be called.

**Wiring.** `resolveCartRecoveryContext` runs once per call in `stream.ts`'s `"start"` handler
(`:1480`), stored call-scoped (`:172`), passed as `cartRecovery` through `runVoiceAgentTurn` (`:1230`)
into `buildVoiceTools(orgId, enabledTools, onSlowToolCall, cartRecovery)`. The tool is removed from the
static `voiceTools` map, so no unbound instance can be handed out. Text test-chat and the synthetic-test
harness deliberately never get it — neither has a real checkout, and a synthetic run must not mint live
Shopify discount codes. No migration, no schema change: this reads state the workflow engine already
persists.

`docs/agent-prompts/01-cart-recovery-agent.md` updated to match — Tools row is now
`offerCartRecoveryDiscount({ reason })` ("you do not choose the discount amount"; if the tool isn't in
your tool list, no discount is configured → skip to Step 5), and Step 4 reads "you decide *when*, the
merchant decides *how much*" with the hardcoded "10% off" example removed. `clampDiscount`
(`workflows/variables.ts:3-4`) is demoted to a sanity bound on merchant input, not a model guardrail.

Decision recorded in
`../decisions/adr-064-the-merchant-owns-the-discount-amount-the-model-owns-only-the-timing.md`
(including the three rejected alternatives: prompt instruction, register-at-0%, org-default fallback).
26 new tests — 20 in `offerCartRecoveryDiscount.test.ts` (bound percentage wins over model-supplied args,
retry safety, `reason` audit trail, schema shape is exactly `["reason"]`, description contains the %,
createDiscount-throws path, 11 `resolveCartRecoveryContext` gate cases) and 6 in `agent.test.ts`
(not registered without context; registered with it; **not** registered from `toolsEnabled` alone;
`toolsEnabled` narrowing still wins; absent from static `voiceTools`).
