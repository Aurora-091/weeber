reproducible gap between the documented decision and the shipped behavior, not a hypothetical: any
org with exactly one agent configured today gets the old plain-heading treatment, not the "always
visible" pill the ADR describes.

overflow/search handling visible — would just wrap onto more rows).

**Recommendation**: either make the single-agent case also render the pill row (with just one pill in
it) for true "always visible, consistent chrome" as documented, or correct the ADR's wording to match
the actual (reasonable) single-agent fallback. Either is a small, low-risk fix — flagging as a
decision, not silently picking one.

## 🔴 P1 — Escalating-discount config panel can produce a silently-broken `"-Infinity"` attempt key

`NodeConfigPanel.tsx`'s `EscalatingMap` component (`CallFields`' escalating-discount mode) lets a
merchant/admin remove every attempt entry down to an empty map via its `x` button (`removeEntry`),
with no floor preventing the last entry from being deleted. Clicking **+ Add attempt** immediately
afterward computes the next key as:

```js
const next = String(Math.max(...Object.keys(map).map(Number)) + 1);
```

`Object.keys({})` is `[]`; `Math.max()` called with zero arguments returns `-Infinity` per spec; the
new entry is inserted as key `"-Infinity"` instead of `"1"`. This isn't just a cosmetic glitch — it's
**silently revenue-relevant at runtime**: `resolveDiscountPercent()` (`voice/workflows/variables.ts`)
looks up `config.discountPercent[String(attemptNumber)]`, i.e. keys `"1"`, `"2"`, `"3"`, ... A map
that only contains `"-Infinity": 0` (or any map missing the real attempt keys) causes every lookup to
miss and silently fall back to `?? 0` — the org's configured escalating discount does nothing on any
call, with zero error surfaced anywhere: not in the editor, not in the save-time `validateGraph()`
check (which only validates graph *shape* — trigger existence, edge references, conditionalSplit
default edges — never node *config content*), not in logs, not on the dashboard. A merchant could
set up "10% off on retry 2, 20% off on retry 3," hit this bug once while editing, and have every
subsequent cart-recovery call quietly offer 0% off indefinitely.

Contrast with the flat-discount path, which the codebase already defends in depth:
`clampDiscount()` clamps to `[0, 30]` at read time (verified by `graph-engine.test.ts`'s existing
`clampDiscount` unit tests) — so an out-of-range flat percent typed in the UI is at least neutralized
server-side, even though the client-side `min={0} max={30}` on that `<Input>` is cosmetic-only
(HTML `min`/`max` on `type="number"` doesn't block invalid `onChange` values, and nothing here
clamps client-side either). The escalating path has no equivalent runtime safety net for a
malformed key — the value at each key is clamped, but a key that never matches any real attempt
number is invisible to that defense.

**Fix options** (not picked here, per your "analysis not code changes" preference):
- Client-side: guard `removeEntry` so it can't delete the last remaining entry, and/or fix
  `addEntry`'s `next` computation to fall back to `"1"` when the map is empty
  (`Object.keys(map).length === 0 ? "1" : ...`).
- Server-side (defense in depth, matching the flat-discount pattern): `validateGraph()` or
  `resolveDiscountPercent()` could reject/ignore non-numeric attempt keys, or `validateGraph()` could
  warn if a `call` node's escalating map is empty or has no `"1"` entry.

## 🟡 P2 — No client- or server-side validation on `delayMinutes` (Wait node)

`WaitFields`' `<Input type="number" min={1}>` is, like the discount fields, a cosmetic-only bound —
`onChange={(e) => set("delayMinutes", Number(e.target.value))}` passes the raw typed value straight
through with no clamp. Unlike `discountPercent`, there is **no server-side floor either** —
`graph-engine.ts` uses it directly: `const delayMs = config.delayMinutes * 60 * 1000;`. A merchant
typing `0` or a negative number (both reachable through the UI — `min` doesn't block them) produces
a zero or negative delay with unverified downstream behavior (whether the scheduler treats a
negative/immediate `runAt` as "now" gracefully or misbehaves wasn't traced this round — flagging as
open, not claiming it crashes). Lower severity than the discount bug since it doesn't look silently
correct (a 0-minute wait is at least an obviously-odd number to spot in the editor), but it's the
same missing-defense-in-depth pattern.

## 🟡 P2 — "Load example" is a silent, unconfirmed destructive overwrite (and its icon says the opposite of what it does)

`dashboard/workflow-editor.tsx`'s toolbar button uses the `Download` lucide icon and reads "Load
example," but its handler (`loadExample`) unconditionally replaces the entire current canvas —
`setNodes(n); setEdges(e);` — with the seed cart-recovery graph, with **no confirmation dialog**,
even when `dirty` is already `true` (i.e. the editor already knows there's unsaved work). This is the
one in-app action that can destroy unsaved edits without so much as a native `confirm()`, in an
editor that otherwise clearly cares about this exact class of problem — see the next item.

Two separable issues packaged together here:
1. **Icon/label mismatch**: `Download` conventionally means "export/save a file to my machine" —
   the opposite of what this button does (load a demo *into* the canvas). Traces and closes out
   audit #04's "admin export/Download feature — imported but not traced" item: there is no
   export/download feature anywhere in this editor; the import is solely (mis)used as decoration on
   an unrelated action.
2. **No guard on a destructive action**: trivially fixable given `dirty` is already tracked —
   `if (dirty && !window.confirm(...)) return;` before replacing state, or reuse whatever pattern
   `deleteSelected` might eventually want too (currently also has no confirmation, though deleting a
   single selected node/edge is much lower-blast-radius than replacing the whole graph).

## 🔴 P1 — Workflow Canvas: node creation is 100% mouse-only, with no accessible fallback

This is the accessibility pass audit #04 flagged as not-yet-done. Grepped the entire canvas
component set (`WorkflowNode.tsx`, `NodePalette.tsx`, `BranchEdge.tsx`, `NodeConfigPanel.tsx`) plus
both host pages (`dashboard/workflow-editor.tsx`, `app/workflows.tsx`) for `aria-`, `role=`,
`tabIndex`, and `onKeyDown` — the **only** hits anywhere are decorative `aria-hidden` on lucide icons
in the surrounding toolbar. Zero `role`, zero `aria-label`, zero keyboard handling on the canvas
itself.

Concretely, the worst single finding: `NodePalette.tsx` — the sidebar list a user drags nodes from
onto the canvas — implements adding a node purely via native HTML5 drag-and-drop
(`draggable` + `onDragStart`, no `onClick` anywhere in the file). **There is no way to add a node to
a workflow graph without a mouse.** This isn't a missing-polish item; it's a complete exclusion of
keyboard-only and most screen-reader users from the single most fundamental authoring action in the
editor — everything downstream (configuring a node, connecting edges, deleting) is moot if a user
can never place a node in the first place.

Node *selection* (`onNodeClick` in the editor pages) and *deletion* (a real `<Button onClick={...}>`)
are at least keyboard-reachable once a node already exists on the canvas — but whether an existing
node can be *selected* without a mouse click depends on `@xyflow/react`'s own default keyboard
handling, which isn't configured or overridden anywhere in this code (no `nodesFocusable`,
`disableKeyboardA11y`, or similar prop set) — not traced this round, flagging as unverified rather
than assuming either way.

**Scope note, not a bug**: consistent with audit #04's observation that the canvas has no mobile
layout, a full accessibility remediation here (keyboard node placement, focus management, live
region announcements for graph changes) is a real, non-trivial feature addition, not a quick fix —
recording it as a confirmed, scoped gap for whoever picks this up next, not something to silently
patch as a one-line change.

## 🔴 P0 — CRM sync + appointment booking: zero multi-tenant support, real cross-org data-leak risk if ever enabled

Expanded scope per follow-up request: audited the agent/tool pipeline and its external integrations,
not just the canvas UI. Found a systemic gap affecting **four** of the platform's built-in voice
tools, all sharing the same anti-pattern:

| Tool | Integration file | How it's configured |
|---|---|---|
| `crmSync` | `voice/integrations/{gohighlevel,salesforce,hubspot}.ts` | Bare `process.env.GOHIGHLEVEL_API_KEY` / `SALESFORCE_ACCESS_TOKEN` / `HUBSPOT_API_KEY`, checked in that priority order |
| `bookAppointment` | `voice/integrations/google-calendar.ts` | Bare `process.env.GOOGLE_CALENDAR_ACCESS_TOKEN` / `GOOGLE_CALENDAR_ID` |

**Confirmed by reading the actual tool `execute()` functions, not inferred**: none of the four take
an `orgId`, none of the four integration modules query the database for per-org credentials — every
single one reads a single, global, server-wide environment variable. Contrast this with how Twilio is
handled (`orgs.twilioAccountSid`/`twilioAuthToken`, real per-org sub-accounts, BYO-or-platform mode,
this session's own C2b work) or how Shopify is handled (`shop_links` table, real OAuth, a whole
dedicated Integrations page) — both of those are genuinely multi-tenant. CRM sync and calendar
booking were clearly built as a single-pilot-customer fast path and never lifted to the same
standard, and nothing in the product surface discloses that gap to anyone configuring an agent.

**Why this is P0, not just a missing feature**: if any of these five env vars is ever set with real
production credentials (which is the entire point of having them), **every org on the platform
whose agent has `crmSync`/`bookAppointment` enabled shares that exact same CRM account / calendar** —
Org A's caller's name, phone number, and call notes get pushed into whatever single GoHighLevel/
Salesforce/HubSpot account the platform operator happens to have configured, and Org B's appointment
bookings land on the same single Google Calendar as Org A's. For the clinic vertical specifically —
where `bookAppointment` is a core, advertised use case, not an edge feature — this means real patient
booking data could cross between unrelated clinic customers the moment this is switched on for more
than one paying org. This is exactly the kind of tenant-isolation bug that's invisible in a demo/pilot
(one customer, looks perfectly fine) and only surfaces once a second paying customer turns the same
feature on.

**Confirmed via UI trace**: neither `pages/app/integrations.tsx` (Shopify/commerce-only — its own
`<PageHeader>` description literally says "Connect commerce platforms," no CRM/Calendar section
exists) nor any other merchant or admin page has any CRM- or Calendar-connection UI at all. A
merchant has no way to know this gap exists, no way to connect their own CRM/Calendar, and — since
`crmSync`/`bookAppointment` are presumably in the default `enabledTools` set for relevant verticals —
may not even realize their agent has these tools active.

**Recommendation** (analysis only, not built): before enabling either of these for any second real
paying org, either (a) gate both tools out of `enabledTools` entirely until proper per-org credential
storage + a connect UI exists (same pattern as Twilio/Shopify), or (b) if there's currently exactly one
paying org using them, that's the only reason this hasn't already caused a visible incident — flag it
loudly rather than treating "hasn't broken yet" as "safe."

## 🟡 Workflow authoring: merchants can tune values, never create/restructure — confirmed intentional, but worth re-examining with concrete options

Re-verified against current code (not just audit #04's note) that this is deliberate, consistently
enforced in two places:

- **No creation path at all for merchants**: `dashboard/workflows-list.tsx` (admin) has a real
  "New workflow" button, a create dialog, and a `POST` mutation. There is no equivalent file, route,
  button, or endpoint anywhere under `pages/app/` — `UserWorkflowsListPage` only ever calls
  `GET /api/app/workflow-configs`, which returns templates already assigned to the org's vertical.
  Its own copy is honest about this: *"Click a workflow to customize timings and messages"* — it
  doesn't pretend to offer more.
- **No structural editing even on assigned templates**: `UserWorkflowEditorInner`'s `<ReactFlow>` is
  `nodesDraggable={false} nodesConnectable={false}` — a merchant can click an editable node
  (`wait`/`call`/`sms` only, via `EDITABLE_TYPES`) to open a side-panel form, but can never add,
  remove, rewire, or reposition a node. This matches audit #04's characterization exactly: *"the
  correct trust boundary, not an oversight."*

**Since you asked to revisit this explicitly, here are the real options, not just a restated
observation:**

1. **Status quo (current)** — admin authors/owns workflow structure per vertical, merchants tune a
   fixed set of values. Lowest risk (a merchant can't break call-routing logic or leave a
   conditionalSplit with no default edge), lowest merchant flexibility. Reasonable default for a
   managed vertical SaaS where "workflow templates are part of the product," not a general-purpose
   automation builder.
2. **Merchant "duplicate and customize"** — let a merchant clone an existing assigned template into
   an org-private copy, then edit *that* copy with the same restricted node-value-only UI (still no
   structural editing) — gets them a workflow that's "theirs" without exposing the full graph editor
   or its P1 config-validation gaps (the `-Infinity` bug, missing `delayMinutes` clamp) to a much
   larger, less technical audience than the current admin-only surface.
3. **Full merchant graph editor (the literal ask)** — reuse `dashboard/workflow-editor.tsx`'s
   `NodeConfigPanel`/`NodePalette`/drag-drop editing for merchants too. Real cost: every validation
   gap found in this audit (escalating-discount `-Infinity` bug, unclamped `delayMinutes`, mouse-only
   node creation with zero accessible fallback, no confirmation before destructive actions) currently
   sits behind an admin-only wall — opening this to every merchant multiplies the blast radius of
   each one and makes the P1 fixes above a hard prerequisite, not a nice-to-have, before this option
   is safe to ship. Also needs new backend authorization (today's structural edits go through
   admin-only routes/`requireAdminKey` in `voice/workflows/admin-routes.ts` — a parallel org-scoped
   write path with the same `validateGraph()` checks would need to be built, not just a frontend
   change).
4. **Middle ground** — keep structure admin-owned, but let merchants add/remove *escalating-discount
   attempt tiers* and *conditionalSplit outcome selections* specifically (the two config shapes that
   are collection-like, not the graph shape itself) without full node/edge editing. Directly answers
   your "variable changing" ask below at lower risk than full graph access.

No option is picked here — flagging as a real product decision with real tradeoffs, per the same
"needs a design decision, don't silently default" rule this whole audit series has followed.

## 🟡 Variable / merge-tag system: the UI under-exposes what the engine actually supports, and the fixed tag list isn't vertical-aware

Traced `renderTemplate()` (`voice/workflows/variables.ts`) end to end: it's a fully generic
`{{key}}` substitution against whatever `context` object the workflow run happens to carry —
**any** key present in `context` gets substituted, not just a fixed allowlist. `context` itself is
seeded from `run.context` (set by whatever triggered the run — a Shopify webhook payload today) and
mutated as the run progresses (`context.attempt_number`, `context.discount_percent`,
`context.discount_code`, `context.cart_recovery_url` are all set inside `graph-engine.ts` itself,
mid-run). So the **runtime is already more flexible than any editor UI lets a user see or use.**

The problem is entirely on the discoverability side: `components/canvas/types.ts`'s `MERGE_TAGS`
constant is a single hardcoded array of 10 Shopify-cart-recovery-specific names (`cart_value`,
`checkout_url`, `shop_name`, `abandoned_checkout_url`, `cart_recovery_url`, ...), imported and shown
**identically** in both the admin `NodeConfigPanel.tsx` and the merchant `workflows.tsx` — there is no
vertical branching at all (confirmed: `MERGE_TAGS` has exactly one import site pattern, no
insurance/clinic-specific variant exists anywhere). An insurance/clinic-vertical admin authoring an
appointment-reminder SMS template sees "cart_value / checkout_url / shop_name" as the suggested
merge tags — none of which apply to their vertical — while genuinely-available fields like
`to_number`, `checkout_token`, or anything a clinic-specific trigger might set on `context` are
invisible in the UI even though `renderTemplate` would happily substitute them if someone already
knew to type `{{to_number}}` blind.

**This directly answers your "variable changing" ask**: the underlying capability to use custom
variables already exists and needs no backend change — the gap is purely that the editor UI doesn't
expose it. A merchant/admin today can only use the 10 hardcoded tags they can see; they cannot
discover or confidently use anything else, even though the engine would honor it.

**Recommendation** (options, not a pick):
- Smallest fix: make `MERGE_TAGS` vertical-aware (a `Record<Vertical, string[]>` keyed the same way
  `verticals.ts` already keys nav/copy/glossary per vertical), so a clinic template shows
  clinic-relevant tag names instead of Shopify ones.
- Bigger, more correct fix: derive the "available tags" hint list dynamically from whatever
  `context` keys the specific workflow's trigger type actually populates, rather than a hand-maintained
  constant that will drift out of sync with `graph-engine.ts`'s actual context-mutation logic (as it
  already arguably has — `to_number`/`checkout_token` are real, usable context keys today with no UI
  presence at all).
