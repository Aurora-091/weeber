## Defects — Priority Ordered

### 🔴 P0 — Fixed during this audit

**D1. `tsc` was actually failing on `main`.** `packages/api/src/voice/routes.test.ts` had two unused-parameter
errors (`noUnusedParameters` violation) that `bun run typecheck` (`tsc --noEmit`) correctly caught — this
tsconfig is a real, non-solution-style config, so the check works (unlike the historical ADR-024 bug), but
nobody re-ran it before this commit landed on `main`. **Fixed in this audit** (prefixed the two unused mock
params with `_`), re-verified: `tsc --noEmit` now exits 0. This is exactly what branch protection on `main`
(flagged as an open action item since the very first `CLAUDE.md`, still not enabled) would have caught before
merge, not after.

### 🟠 P1 — Real, not yet fixed, needs a decision before a fix

**D2. `eraseOrgDataForPhoneNumber`'s `callerMemory` deletion is not org-scoped.** In
`packages/api/src/voice/compliance/adapters.ts`, the GDPR erasure function correctly scopes the `calls` table
deletion to `(orgId, phoneNumber)` — but the `callerMemory` deletion is `WHERE phoneNumber = ?` only, with no
`orgId` filter (the `callerMemory` table has no `orgId` column at all — it's structurally global, one row per
phone number, by original design intent for cross-call memory).

**Concretely:** if the same phone number interacts with two different Weeber merchants (plausible — it's the
same person, calling two different stores that both use Weeber), a GDPR erasure request submitted through
**Merchant A's** Shopify store will delete that number's caller memory **for Merchant B too**, silently.

This is not a typo-level bug — it's a real, undecided product/compliance question: should a redact request
scoped to one merchant's data relationship also wipe a shared phone number's cross-call memory globally? Each
merchant is arguably a separate data controller and should likely only erase what *they* hold. **No test
covers this scenario** — the existing redact test (`routes.test.ts`) only verifies single-org deletion, not
the cross-org leak. Recommend: decide the intended behavior explicitly (this is exactly the kind of
compliance-package-adjacent change that should go through `CLAUDE.md` gate #6, confirm with the user before
changing), then add the missing test either way.

**D3. Two substantial commits landed with zero ADR entries — a recurring pattern, not a one-off.** The
`feat(backend): implement workstreams A, J, K, L, M, N` and `feat(backend): implement structured logging and
custom error handling framework` commits (real, non-trivial architecture — new tables, a new persona
resolution hierarchy, a new logging framework) have no matching entry in `DECISIONS.md`. Instead, a new
`changelog.md` (lowercase, root-level) was created as a parallel tracking document. This is the **second**
time in this repo's history a batch of real work skipped the ADR discipline this project's own conventions
establish (the first was the OSS-cleanup + backend-split batch, later caught and not backfilled). Two
consequences: (a) the reasoning behind real decisions in this batch — e.g. why the attribution window is 7
days now, not the 72h originally noted in ADR-030's own gap list — isn't recorded anywhere, and (b)
`changelog.md` and `DECISIONS.md` are now two competing sources of truth for "what changed and why," with no
stated rule for which one is authoritative. Recommend either backfilling an ADR-039 for this batch, or making
an explicit call that `changelog.md` replaces ADR entries for routine feature work (and saying so in
`CLAUDE.md`) — but not letting both exist ambiguously.

### 🟡 P2 — Real, low urgency

**D4. `recoveredAmount` is stored as `text`, not a numeric type.** In `scheduled_calls`, `recovered_order_id`
and `recovered_amount` are both `text` columns. `recoveredOrderId` as text is fine (it's an identifier, not a
number to compute with). `recoveredAmount` being text means any future revenue-attribution dashboard summing
recovered value has to cast on every query, and is exposed to formatting inconsistency (e.g. `"599.00"` vs
`"599"` vs a currency symbol slipping in) silently breaking aggregation. Cheap to fix now (per this repo's own
"no production data yet" reasoning from ADR-034) — a real migration cost once real orders exist.

**D5. Attribution window changed from 72h (ADR-030's own gap note) to 7 days, undocumented.** Not
necessarily wrong — a 7-day window is arguably more realistic for cart-recovery-to-purchase attribution — but
it's a behavior change from what was explicitly written down before, with no ADR explaining the reasoning.
Tie this into fixing D3.

### 🟢 P3 — Minor, worth knowing, not urgent

**D6. Per-scheduled-call org lookup in the sweep loop is an N+1 query pattern.** `scheduler.ts`'s
`executeDueScheduledCalls` now does one extra `SELECT` against `orgs` per due row with an `orgId`, inside the
sweep's `for` loop, to resolve the per-org outbound number. Fine at current volume (a 60-second sweep with a
handful of due calls); worth batching or caching if scheduled-call volume grows meaningfully.

**D7. `resolvePersona` adds up to 3 sequential DB round-trips to call setup, unmeasured.** Correctly invoked
once per call (not per turn — verified the only call site, in `stream.ts`, is at session setup), so this
isn't a hot-path-per-turn problem. But it does add real, currently-unmeasured latency to time-to-first-
greeting, and isn't captured by the existing per-call latency breakdown (ADR-022 tracks STT-connect/LLM-TTFT/
TTS-first-byte specifically, not session-setup time before those). Worth adding a timing point here if
greeting latency ever becomes a complaint.

**D8. `changelog.md` (new, lowercase) reintroduces a document structurally similar to `CHANGELOG.md`**
(uppercase), which was deliberately deleted during the OSS-cleanup commit as "OSS-only scaffolding, not
needed" for the private fork. Not wrong to want a changelog — worth deciding if this is the same kind of
document coming back under a new name, or something genuinely different, and naming/placing it accordingly.

## Resolution (same-day follow-up, post-audit)

User reviewed this audit and made three explicit decisions:

1. **D2 → org-scoped.** `callerMemory` now has an `orgId` column, primary key changed to
   `(org_id, phone_number)`, erasure and reads scoped accordingly. See `changelog.md`'s 2026-07-10 entry for
   the full change list and the new regression test in `packages/api/src/voice/compliance/adapters.test.ts`.
   No ADR opened for this — see decision 3 below.
2. **D1 fix + this audit file → committed and pushed to `main`,** along with the D2 fix, in the same session.
3. **D3/D8 (ADR vs `changelog.md`) → resolved: `changelog.md` is now the source of truth for routine feature
   work going forward.** `DECISIONS.md`/ADRs remain reserved for real architectural/compliance decisions.
   `CLAUDE.md` updated with this rule and the test to distinguish the two. D2 itself, despite touching
   compliance-adjacent code, was treated as a bugfix-with-user-confirmation (gate #6 satisfied by the
   explicit decision above) rather than a fresh ADR, consistent with this new rule.

Branch protection on `main` (recommendation #2 in this audit) is still **not enabled** — remains the top
outstanding action item for next session.
