### 🟠 P1 — First-login org-bootstrap has a real race condition — ✅ FIXED

**`packages/api/src/app/routes.ts`'s `resolveOrCreateMembership`** (used by `GET /api/app/me`, the one
route that runs the first-login bootstrap) has a comment claiming: *"Idempotent under races — the unique
(user, org) index plus re-select means two concurrent first requests still end up with exactly one
membership."* This is not actually true given the current schema.

`org_members`'s only uniqueness constraint (`schema.ts` line ~203) is a **composite** index on
`(supabase_user_id, org_id)`, not a standalone unique constraint on `supabase_user_id` alone. The
bootstrap function generates a fresh `randomUUID()` org id **before** attempting the insert, on every
call. Two concurrent first-login requests for the same brand-new user each generate a *different*
`orgId`, so their two `INSERT ... ON CONFLICT DO NOTHING` calls never actually conflict with each other —
the composite key `(userA, orgA)` and `(userA, orgB)` are both distinct rows, both inserts succeed, and
the user ends up with two separate orgs and two membership rows. The re-select afterward
(`.limit(1)` with no `ORDER BY`) then returns whichever row the query planner happens to pick first —
non-deterministic across the two concurrent requests, meaning the two requests can disagree about which
org "won."

**Why this matters in practice:** a double-click on "sign in," two browser tabs open during first login,
or a slow network causing a client-side retry are all realistic ways to trigger two near-simultaneous
`GET /me` calls for the same brand-new user. The result is a split-brain org — data (agent configs, call
history) written under one org id while the dashboard might resolve to the other on a subsequent load,
which looks like data randomly disappearing/reappearing to the user, and is a real support/trust problem
for a paying customer, not just a theoretical race.

**Fixed during this audit** (confirmed no existing production data would violate it first — checked
`org_members` for any `supabase_user_id` with more than one row: zero found): schema.ts's composite
`org_members_user_org_idx` replaced with a real standalone unique index on `supabase_user_id` alone
(migration `0019_chubby_terrax.sql`, applied to the live DB, verified via `pg_indexes`). One accepted
residual: under the race, the *losing* request's `orgs` insert still succeeds (org ids are always unique
random UUIDs, so that insert never conflicts) — it just never gets a membership row pointing to it,
leaving one harmless orphaned org row. Not worth the added transactional complexity to prevent — no data
is ever written to an orphaned org, and the actual reported problem (a user's own view splitting across
two orgs) is fully fixed.

### 🟠 P1 — JWKS verification does a live fetch on every request when `SUPABASE_JWT_SECRET` is unset — ✅ FIXED

**`packages/api/src/app/middleware/supabase-auth.ts`**'s top comment claims: *"A network round-trip to
ap-south-1 on every API call (`supabase.auth.getUser`) would buy only instant revocation... Hono caches
the key set"* — justifying the JWKS-based `verifyWithJwks` path as the lower-cost alternative. Traced the
actual imported function (`hono/jwt`'s `verifyWithJwks`, in
`node_modules/hono/dist/utils/jwt/jwt.js`): it does a **plain, uncached `fetch(jwks_uri)` on every single
call**, with no in-memory cache, no `Cache-Control`/ETag handling, nothing. There is no caching happening
at all in this code path — the comment describing Hono as caching the key set is incorrect.

**Confirmed active, not just conditional:** checked Railway's production env vars directly (via the
Railway GraphQL API) — `SUPABASE_JWT_SECRET` is **not set**. The JWKS branch is genuinely the live path,
meaning every authenticated `/api/app/*` request was doing a live network round-trip to Supabase's JWKS
endpoint before this fix.

**Fixed during this audit:** `supabase-auth.ts` now fetches the JWKS document itself (instead of handing
`jwks_uri` to `verifyWithJwks`, which is what triggered the uncached per-request fetch) and caches the
returned keys in-memory for 10 minutes, passing `keys` to `verifyWithJwks` instead. Accepted tradeoff: no
retry-on-cache-miss logic for the rare case of a key rotation landing mid-TTL-window — the 10-minute
window is short enough to self-heal without that complexity. Verified: typecheck clean, 191/191 api tests
still pass.

### 🟡 P2 — `ADR-043` is now stale, and `reset-password.tsx` is dead code — ✅ DOCS FIXED, CODE KEPT AS-IS

`DECISIONS.md`'s ADR-043 states as its decision: *"Password reset is the one flow that keeps its link (the
`/app/auth/reset-password` page works off the recovery token in the URL)... the redirect allowlist now
only matters there."* This was true when written (2026-07-10), but is **no longer true** — the recovery
email template (`supabase/templates/recovery.html`) was silently switched to fully code-based (renders
only `{{ .Token }}`, no `{{ .ConfirmationURL }}` at all, per its own header comment: *"OTP-only (ADR-043
extended)"*) as part of this session's hosted-Supabase-config-sync work, and `login.tsx`'s forgot-password
flow now does a complete 3-step inline OTP verification (`verifyOtp({ type: "recovery" })`) — no link
involved anywhere.

That silent extension was never given its own ADR entry — it's referenced only as "ADR-043 extended" in
a template file's comment, with no corresponding decision record explaining *why* the one-link-flow ADR-043
called out as intentional got superseded. This is exactly the kind of doc drift these audits exist to
catch (same category as this session's own `docs: fix stale dashboard.md` commit).

**Consequence:** `packages/web/src/web/pages/app/reset-password.tsx` and its route
(`appPath("/auth/reset-password")` in `app.tsx`) are now unreachable through the normal product flow —
Supabase will never send a link for the user to land on that page via. `supabase/config.toml`'s own
comment calls it a "fallback route" for "any future OAuth flow," but no OAuth flow exists in this codebase
today, so that justification is speculative, not concrete.

**Resolved:** user's explicit call was to keep `reset-password.tsx` as speculative future-OAuth
scaffolding rather than delete it — written up as **ADR-053**, which formally corrects ADR-043's now-false
claim and documents the keep-it-around decision (with the actual reasoning: it's cheap since it's
lazy-loaded and never fetched unless routed to, and its `onAuthStateChange`/session-detection pattern is
plausibly reusable if an OAuth provider is ever added). No code changed for this finding — it's a pure
documentation fix.

### 🟡 P2 — No error boundary around the newly-lazy-loaded route tree — ✅ FIXED

This session's subdomain-split work (`47fd6fb`) converted every page in `app.tsx` to `React.lazy()` for
real bundle-size isolation between surfaces — a good, verified change. But it introduced a new failure
mode that didn't exist when everything was a static import: a lazy `import()` can reject at runtime (most
commonly: a user has an old tab open, a new deploy invalidates the old build's chunk hashes, the user
then navigates and the browser 404s fetching a chunk that no longer exists). There is no `ErrorBoundary`
anywhere in `app.tsx` or `components/provider.tsx` to catch that — searched explicitly, found nothing.
Today, that failure mode white-screens the tab with an uncaught error instead of showing a "new version
available, please reload" prompt, which is a materially worse experience than what existed before the
lazy-loading refactor (a stale JS bundle that at least still ran, until the user's next hard navigation).

**Fixed during this audit:** new `components/chunk-error-boundary.tsx` (`ChunkErrorBoundary`), a narrow
class-component error boundary wrapping the `<Suspense>` block in `app.tsx`. Recognizes the specific error
shapes browsers/Vite throw for a failed dynamic import ("Failed to fetch dynamically imported module",
"error loading dynamically imported module", "Importing a module script failed") and shows a "Reload"
button; anything else re-throws normally rather than being silently swallowed, so this stays a targeted
fix, not a catch-all error boundary for the whole app. Verified: typecheck clean, all four surface builds
(`public`/`admin`/`user`/`all`) still succeed with the same bundle sizes as before this fix (purely
additive, no bundle-size regression).

### 🔵 New finding — `PUBLIC_WEB_URL` on Railway still points at the old `openvent-api.vercel.app`, silently defeating last week's referral-link fix

Surfaced while checking whether `SUPABASE_JWT_SECRET` is set (same Railway variables query). Commit
`5678ab3` ("fix(waitlist): referral email links land on the marketing site, not the API origin") changed
the code to build referral links from `PUBLIC_WEB_URL`, falling back to `https://www.weeber.ai` if unset —
but `PUBLIC_WEB_URL` is **already set** on Railway, to `https://openvent-api.vercel.app` (the old,
pre-rename Vercel project name, from before this session's subdomain split). Since the env var is set,
the code's fallback to `www.weeber.ai` never triggers — referral links in waitlist emails are still
pointing at a URL that, while it happens to still resolve (that Vercel project is the one now serving
`www.weeber.ai`'s content under its old name, per this session's earlier project-rename work), is not the
canonical domain and won't survive if that project is ever fully retired/renamed again.

**Not fixed during this audit** (Railway env var change — a deploy-affecting production config change
outside the scope of what was pre-approved this round; flagging for your call rather than changing it
unasked). **Suggested fix:** update `PUBLIC_WEB_URL` on Railway to `https://www.weeber.ai`.

## What I verified as solid (not just trusted from commit messages)

- **JWT signature verification correctness**: `verifySupabaseJwt` correctly branches HS256 (shared
  secret) vs. RS256/ES256 (JWKS), explicitly disallows symmetric algorithms on the JWKS path (Hono's
  `verifyWithJwks` throws `JwtSymmetricAlgorithmNotAllowed` if a token claims an HMAC alg while using the
  JWKS branch) — no algorithm-confusion vulnerability.
- **Org-scoping**: every route below `/me` in `app/routes.ts` reads `orgId` exclusively from the resolved
  session (`c.get("userOrgId")`), never from a path param or request body — consistent with the
  cross-tenant-isolation discipline flagged as solid in audit #02.
- **Password-reset OTP flow itself**: `login.tsx`'s 3-step forgot-password (email → code → new password)
  is correctly implemented — `resetPasswordForEmail` → `verifyOtp({ type: "recovery" })` →
  `updateUser({ password })`, no `redirectTo` needed or passed (correct, since it's code-only).
- **Merchant→User rename + subdomain split**: independently re-verified live against
  `www.weeber.ai`/`admin.weeber.ai`/`app.weeber.ai` this session (not just re-reading the diff) — matches
  documentation exactly, including the `VITE_APP_SURFACE=merchant` backward-compat shim working correctly
  before being safely removed once the Vercel project was confirmed flipped.
- **Full CI**: typecheck (3 packages), 233/233 tests, lint, and build all genuinely clean on a fresh
  `bun install`, not a stale `node_modules`.
