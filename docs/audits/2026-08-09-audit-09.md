# Audit 09 — pre-pilot risk audit (2026-08-09)

**Commit audited:** `cf929b0` (branch `main`, 2026-08-09)
**Previous audit baseline:** `2eb819e` (audit #08, 2026-07-30)
**Method:** source-level only. No database, no Railway/Vercel access, no live traffic, no analytics,
no production env vars. Every finding below is derived from the code in this repo at `cf929b0`.
Anything that depends on runtime configuration is flagged as unverifiable rather than asserted.

---

## Verdict

The codebase is in better shape than the audit count suggests. Baseline is genuinely green — not
"green if you skip the slow suite":

| Check | Result |
| --- | --- |
| `bun install --frozen-lockfile` | exit 0 |
| `bun run typecheck` | exit 0 (3 packages) |
| `bun run lint` | 0 warnings, 0 errors |
| `bun run test` | exit 0 — **1111 tests** (966 api, 74 web, 71 compliance) |

Drift since audit #08 is large: **60 commits, 330 files, +33,527 / −1,133** across ten days. Total
TS/TSX source is 71,530 LOC. A change of that size normally produces a crop of new correctness bugs.
It mostly didn't. The concurrency-sensitive paths I went after are correct — scheduler claims use an
atomic conditional `UPDATE` (multi-instance safe, `voice/workflows/scheduler.ts:143`), the outbound
rate limiter is Postgres-backed per-org rather than in-process, DNC and attempt-caps are not bypassed
by test mode, CORS refuses to boot in production without `CORS_ALLOWED_ORIGINS`, and `/api/app/*`
derives `orgId` from the session (`c.get("userOrgId")`) rather than trusting the request body. ADR-080
documents the inert role model honestly instead of pretending it's enforced. That is unusual
discipline and this audit deliberately does not restate what ADRs 001–080 and audits 01–08 already
cover.

So the finding is not "the code is broken". It's that **the remaining risk has moved out of
correctness and into operations** — money, access, and silence. Three findings are the ones that can
actually damage a first pilot:

1. **F1 — there is no spend ceiling anywhere in the product.** A bug, a loop, or a hostile actor can
   burn real telephony and LLM money with no cap and no alert. This is the single highest-expected-cost
   item in the repo.
2. **F4 — the admin gate fails open.** If `ADMIN_API_KEY` is unset and no labeled key row exists,
   every ops endpoint — call list, transcripts, DNC, force-end — serves unauthenticated, warning once
   to stdout. There is no boot-time env preflight to catch it.
3. **F5 — `claimed` scheduled calls are never reaped.** One restart at the wrong moment permanently
   strands a scheduled call in `claimed` with no error, no retry, and no visibility. The customer
   simply never gets called.

Those three share a shape: the system does the right thing when everything works, and fails quietly
when it doesn't. Pre-pilot that's invisible. During a pilot, a silently undialed customer or a
surprise telephony bill is the thing that ends the pilot.

Pilot gate recommendation: **F1, F4, F5 before the first real outbound call to a real customer.**
Everything else can be scheduled.

## Findings

Severity: **P0** = fix before first pilot call, **P1** = fix before pilot, **P2** = fix during pilot,
**P3** = backlog.

### F1 — No spend or usage ceiling exists (P0)

`packages/api/src/database/schema.ts` defines 43 tables. None of them is a usage, subscription,
invoice, or quota table. Plan is a free-text string on `orgs.planName`. `voice/cost-estimate.ts` is
display-only — it renders a number, it does not gate anything. `rg 'maxConcurrent|MAX_CONCURRENT|concurrency'`
returns zero hits, so there is no concurrent-call ceiling either. No payment provider is integrated
anywhere in the repo.

The only throttle in the entire system is `voice/middleware/rate-limit.ts` — 30 calls/min/org. That
is roughly **1,800 calls/hour/org** with no daily cap, no monthly cap, no per-org budget, and no
alerting when spend accelerates.

**Why it matters:** at the ~$0.06/min all-in COGS this product is priced around, a runaway loop or an
over-eager campaign is a four-figure bill with no circuit breaker and no notification. The failure is
also un-undoable — telephony minutes are spent, not reversible.

**Fix:** a `usage_counters` table keyed `(orgId, period)` incremented on call start and finalized on
call end; a hard per-org daily minute/call cap checked in the same middleware that already does the
per-minute limit; a `maxConcurrentCalls` guard; and one alert at 80% of cap. This is a decision, not
just code — it needs an ADR on what the default caps are and whether hitting a cap fails the call or
queues it.

### F2 — Plivo and Exotel secrets are returned to the admin browser (P1)

`voice/admin-routes.ts:115` and `:156` both select the full `orgs` row and strip exactly one field:

```ts
const { twilioAuthToken: _twilioAuthToken, ...safeOrg } = org;
```

`plivoAuthId`, `plivoAuthToken`, `exotelSid`, `exotelApiKey`, and `exotelApiToken` are returned in
full — by `GET /orgs/overview` (**every org at once**) and `GET /orgs/:orgId`. The consumer,
`packages/web/src/web/pages/dashboard/orgs.tsx`, doesn't even use them, so this is pure gratuitous
exposure: live provider credentials for all tenants sitting in an admin browser's network tab, memory,
and any error-reporting payload that captures responses.

**Fix:** replace the destructure-one-field pattern with an explicit allowlist of columns in the
`db.select({...})` call. Denylists rot every time a column is added — that's exactly how Plivo and
Exotel got in here after the Twilio strip was written.

### F3 — The credential vault is decorative while plaintext columns remain (P1)

`database/credential-vault.ts` implements a proper Supabase Vault / pgsodium path and is vault-first
on read. But provisioning still dual-writes plaintext:

- `voice/twilio-provisioning.ts:68`, `:592`
- `voice/plivo-provisioning.ts:71` — comment says "kept for fallback during vault transition"
- `voice/exotel-provisioning.ts:81`

And `voice/middleware/plivo-signature.ts:46` reads **only** the plaintext column, so the plaintext
copy isn't dead weight — it's load-bearing.

**Why it matters:** the vault's security value is that a DB dump is worthless. With plaintext columns
still populated, a dump is fully worth it. The vault currently buys compliance narrative, not
protection. That gap is fine to hold deliberately; it is not fine to hold unknowingly, and F2 above
shows the plaintext columns leaking through an unrelated endpoint.

**Fix:** finish the transition — point `plivo-signature.ts` at the vault, stop dual-writing, then a
migration that nulls the plaintext columns. Until then, an ADR stating the vault is transitional would
keep the docs honest.

### F4 — Admin authentication fails open (P1)

`voice/middleware/admin-auth.ts:64-75`:

```ts
if (!configuredKey && !(await hasAnyAdminKey().catch(() => false))) {
  if (!warnedMissingKey) { console.warn("... are currently UNAUTHENTICATED ..."); warnedMissingKey = true; }
  c.set("adminActor", "unauthenticated-dev");
  return next();
}
```

If `ADMIN_API_KEY` is unset **and** no labeled admin key row exists, the ops surface — `/calls`,
transcripts, `/dnc`, force-end, `/admin-keys` — is fully open. The mitigation is a single
`console.warn` on first request, in a service whose Railway policy is `restartPolicyType: ON_FAILURE`,
i.e. logs churn routinely.

There is no boot-time env preflight to catch this: `rg 'requiredEnv|assertEnv|validateEnv'` returns
zero hits. `server.ts` does assert HIPAA config, voice config, and CORS origins at boot — but never
the admin key. So the one class of misconfiguration that silently disables authentication is the one
class not asserted.

Secondary: the key comparison is `providedKey === configuredKey`, a non-constant-time compare. Minor
next to fail-open, but free to fix with `timingSafeEqual`.

**I cannot verify whether `ADMIN_API_KEY` is set in production** — that's the point. The code's design
makes "is admin auth on right now?" unanswerable from the repo.

**Fix:** fail closed. In production, refuse to boot without an admin key, exactly as CORS already
does. Keep the open path behind an explicit `NODE_ENV !== "production"` check.

### F5 — No reaper for `claimed` scheduled calls (P1)

`voice/workflows/scheduler.ts:145` and `:268` set `status: "claimed"`. `rg '"claimed"'` shows no code
path that ever un-claims a row — no timeout sweep, no reaper, no requeue. The claim itself is correct
and race-safe; the recovery is missing.

A crash, deploy, or OOM between claim and dispatch strands that row permanently. Nothing retries it,
nothing surfaces it, no error is raised. `ON_FAILURE` restarts make this a routine occurrence rather
than a theoretical one.

**Why it matters:** this is the worst failure mode in a voice product because it is indistinguishable
from success in every dashboard you have. The scheduled call just doesn't happen.

**Fix:** add `claimedAt` and a sweep that returns rows `claimed` longer than N minutes to `pending`
with an incremented attempt count, plus a metric on how many rows the reaper touches — that number is
your restart-during-dispatch rate.

### F6 — JWT claims under-validated (P2)

`app/middleware/supabase-auth.ts:74-108` verifies the signature and requires `sub`. It does not check
`aud`, `iss`, or `role`. Today that is saved by an accident: Supabase anon and `service_role` keys
carry no `sub`, so they're rejected by the `sub` requirement rather than by any deliberate check.

**Fix:** assert `iss` matches your project URL, `aud === "authenticated"`, and `role === "authenticated"`.
Three lines, removes the dependence on a Supabase key-format detail you don't control.

### F7 — PII in stdout logs, and two competing logging systems (P2)

Full E.164 phone numbers are logged at:

- `voice/workflows/scheduler.ts:154, 172, 194, 209, 217, 300`
- `voice/workflows/graph-engine.ts:258, 268, 288`
- `voice/workflows/engine.ts:185, 194, 196`
- `integrations/shopify/routes.ts:186` (raw phone)

`utils/logger.ts` exists as a structured logger with **no redaction**, and most call paths bypass it
for bare `console.log` anyway — so you have two logging systems and neither is safe.

**Compliance consequence:** the GDPR retention sweep purges the database only. It does not touch logs.
So a subject-erasure request is currently satisfied in the DB and unsatisfied in your log retention —
which is a documentation problem as much as a technical one, given the compliance-first positioning.

**Fix:** one logger, a redaction layer that masks E.164 to last-4, and a statement in the retention
docs about log retention windows. Lint rule banning bare `console.log` in `packages/api/src` prevents
regression.

### F8 — 16 dependency vulnerabilities, 9 high, and no CI job that would ever notice (P2)

`bun audit` at `cf929b0`: 16 advisories, 9 high. The one that matters:

- **`hono <4.12.34`** — CORS-middleware ReDoS and a `memo()` cross-user disclosure issue. CORS
  middleware **is** in use at `packages/api/src/index.ts:31`. The fix is inside the existing
  `^4.12.10` range, so this is a lockfile bump, not a migration.
- Transitive noise: `postcss`, `nanoid`, `brace-expansion` (via `exceljs`), `js-yaml` and `ip-address`
  (via `pm2`).

`.github/workflows/ci.yml` runs typecheck, test, build, lint, migration-drift, e2e, design-guard,
visual, a11y, fonts, ci-success. There is **no** `bun audit`, CodeQL, Dependabot, or secret-scanning
job. The pipeline is unusually thorough about design and accessibility regressions and blind to
supply-chain ones.

**Fix:** `bun update hono` now; add a `bun audit --audit-level=high` job plus Dependabot and a
gitleaks pass.

### F9 — No security headers (P2)

No CSP, HSTS, `X-Frame-Options`, `Referrer-Policy`, or `Permissions-Policy` in `vercel.json` (which
sets only cache headers and `X-Robots-Tag`) or in `api/src/index.ts` / `server.ts`.

For a product whose sales motion leans on compliance, this is the cheapest possible credibility fix
and the first thing a security questionnaire or a merchant's IT reviewer checks. Start with
`Referrer-Policy`, `X-Frame-Options`, and HSTS — trivially safe — then a report-only CSP.

### F10 — Unauthenticated hosted lead form (P2)

`app/public-routes.ts:181-221` exposes `POST /api/public/leads/:orgId/form` with no auth. Its limiter,
`hostedFormLimiter = makeFixedWindowLimiter(60_000, 10)`, is **in-process** (useless across instances)
and keyed on a spoofable `x-forwarded-for`.

Today the blast radius is database pollution only — `voice/leads/ingest.ts:90-95` confirms
`triggerWorkflow` is not wired up. **The day it is wired, this endpoint becomes a way for a third
party to make your platform robodial arbitrary numbers on a tenant's account and compliance record.**

**Fix:** before wiring the trigger, add a per-org form token, a captcha or proof-of-work, and move the
limiter to the Postgres-backed limiter you already built for outbound.

### F11 — Unauthenticated `/api/health` leaks configuration (P3)

`index.ts:41-74` returns which provider keys are configured, `hipaaMode`, `dataRetentionDays`, and the
active TTS/LLM providers — to anyone. Split it: a bare `200 OK` for load balancers, and the detailed
payload behind admin auth.

### F12 — Web test coverage is thin relative to its size (P2)

26,330 LOC of web source against 8 test files / 74 tests. The `e2e` job deliberately covers only the
secret-free public landing page. Meanwhile the API has 966 tests over a comparable surface.

The asymmetry means dashboard regressions are caught by you clicking, not by CI — during a pilot, that
becomes caught by the merchant. Highest-value target isn't coverage percentage; it's one authenticated
e2e path per vertical: log in → create agent → schedule call → see it in call history.

### F13 — The system detects degradation and tells no one (P2)

`voice/call-health.ts` classifies calls as `silent-failure` and `degraded` and persists the
classification. The only consumer is an admin list view (`admin-routes.ts:487-495`). No alert, no
email, no webhook, no threshold.

This is the same pattern as F1 and F5, and it's the thematic finding of this audit: **the detection
work is done and the notification work isn't.** You have already paid the hard cost — knowing that a
call failed silently — and you're not collecting the payoff, which is finding out without looking.

**Fix:** one alerting sink (Sentry is presumably already a dependency — I cannot verify `SENTRY_DSN`
is set) and three rules: spend over cap, reaper touched > 0 rows, silent-failure rate over threshold.

## Explicitly verified as correct — do not re-file these

Recorded so a future audit doesn't spend the time again:

- Scheduler claim races — atomic conditional `UPDATE`, multi-instance safe (`scheduler.ts:143`).
- Outbound rate limiting — Postgres-backed and per-org, not in-process.
- DNC and attempt-cap enforcement — not bypassed by test mode.
- CORS — refuses to boot in production without `CORS_ALLOWED_ORIGINS`.
- Tenant isolation on `/api/app/*` — `orgId` from session (`c.get("userOrgId")`), never from body.
- Role model — ADR-080 documents it as inert honestly rather than overclaiming enforcement.

## Limits of this audit

- Source-level only. No DB, no deploy access, no traffic, no analytics.
- Cannot confirm whether `SENTRY_DSN`, `ADMIN_API_KEY`, or `CORS_ALLOWED_ORIGINS` are set in
  production. F4 in particular is unverifiable from the repo by design, which is itself the finding.
- No load or latency testing, so nothing here speaks to the sub-second targets the category is judged on.
- No pen-testing; F2/F4/F10 are read from code paths, not exploited.
